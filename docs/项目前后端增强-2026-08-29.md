## 一、BPCS 全页面导出功能（CSV / Excel / PDF）

### 1.1 需求概述

当前 BPCS 模块 19 个前端页面均无导出功能。BPCS 用户习惯用 Excel 做二次分析，这是最高频需求。项目已有导出基础设施，只需在每个页面接入。

### 1.2 现有导出基础设施分析

| 层级 | 工具 | 文件位置 | 能力 |
|------|------|----------|------|
| **前端 CSV** | `ExportButton.vue` 组件 | `frontend/src/components/ExportButton.vue` | 客户端生成 UTF-8 BOM CSV，无需后端调用 |
| **前端 Blob 下载** | `triggerBlobDownload()` | `frontend/src/api/blobClient.ts` | 通用二进制下载，自动注入 Token + X-AS400-Server 头 |
| **后端 Excel** | Apache POI 5.2.5 | `ReportRenderer.java` | `XSSFWorkbook` 生成 .xlsx，自动列宽 + 粗体表头 |
| **后端 PDF** | OpenPDF 1.3.30（iText fork） | `ReportRenderer.java` | A4 横向，CJK 字体检测（msyh.ttc / simsun.ttc / Noto CJK） |
| **已有导出端点** | `ReportController` / `InspectionController` | 4 个端点 | `GET /api/v1/reports/{type}?format=xlsx\|pdf` |

**结论**：后端 Excel + PDF 渲染能力已完备（`ReportRenderer.java`），前端 CSV 导出组件已完备（`ExportButton.vue`）。缺少的是 **BPCS 页面的导出端点** + **前端导出按钮接入**。

### 1.3 导出格式选择方案

用户在导出时可选择格式：CSV / Excel / PDF。

**推荐方案**：前端导出按钮旁增加格式选择下拉（`el-dropdown`），点击后调用不同端点：

```
┌─────────────────────────┐
│ 导出 ▼                   │
├─────────────────────────┤
│ 📄 CSV（当前筛选数据）    │  ← 前端 Generate，无需后端
│ 📊 Excel（当前筛选数据）  │  ← 后端 /api/v1/bpcs/{module}/export?format=xlsx
│ 📕 PDF（当前筛选数据）    │  ← 后端 /api/v1/bpcs/{module}/export?format=pdf
└─────────────────────────┘
```

- **CSV**：数据量 < 1000 行时推荐，前端直接生成（`ExportButton` 逻辑），零延迟
- **Excel**：数据量大或需要保留格式时推荐，后端 POI 生成（支持多 Sheet、样式）
- **PDF**：需要打印/存档时推荐，后端 OpenPDF 生成（A4 横向，含页眉页脚）

### 1.4 需要新增的后端端点

在 `BpcsExportController.java`（新建）中统一处理所有 BPCS 模块的导出：

| 端点 | 说明 | 参数 |
|------|------|------|
| `GET /api/v1/bpcs/export/orders` | 订单导出 | `format=xlsx\|pdf\|csv` + 查询参数 |
| `GET /api/v1/bpcs/export/customers` | 客户导出 | 同上 |
| `GET /api/v1/bpcs/export/inventory` | 库存导出 | 同上 |
| `GET /api/v1/bpcs/export/shipping` | 发货导出 | 同上 |
| `GET /api/v1/bpcs/export/invoices` | 发票导出 | 同上 |
| `GET /api/v1/bpcs/export/sales` | 销售导出 | 同上 |
| `GET /api/v1/bpcs/export/purchases` | 采购导出 | 同上 |
| `GET /api/v1/bpcs/export/items` | 物料导出 | 同上 |
| `GET /api/v1/bpcs/export/supply-chain/{type}` | 供应链导出 | `type=orders\|alerts\|analysis\|history\|receiving\|abc\|supplier\|kpi\|tracking` |

**实现方式**：复用现有 `ReportRenderer`，传入列定义 + 数据行即可。

## 二、自定义报表构建器 + 定时报表邮件推送

### 2.1 自定义报表构建器

#### 2.1.1 需求概述

拖拽式选择字段 + 过滤条件 + 排序，生成 SQL 查询 BPCS 文件。降低业务人员对开发者的依赖。

#### 2.1.2 技术方案

**架构**：前端拖拽式 UI → 后端动态 SQL 生成 → BPCS 数据库执行 → 结果渲染/导出

**前端**：
- 报表构建器页面（`views/bpcs/reportBuilder/index.vue`）
- 左侧：可用字段列表（树形，按 BPCS 表分组）
- 中间：已选字段拖拽区 + 过滤条件配置 + 排序配置
- 右侧：实时预览（表格 + 图表）
- 顶部：保存/加载/导出按钮

**后端**：
- `BpcsReportBuilderController.java`：
  - `GET /api/v1/bpcs/report-meta/tables` — 返回可用 BPCS 表及字段元数据
  - `POST /api/v1/bpcs/report-meta/preview` — 预览查询（限制 100 行）
  - `POST /api/v1/bpcs/report-meta/execute` — 执行查询（分页）
  - `POST /api/v1/bpcs/report-meta/export` — 导出查询结果
- `BpcsReportBuilderService.java`：
  - 根据用户配置动态生成 SQL（白名单校验字段名/表名）
  - 支持：SELECT（字段选择）、WHERE（过滤）、ORDER BY（排序）、GROUP BY（分组）、HAVING（分组过滤）
  - 安全校验：字段名/表名必须在元数据白名单内，禁止 UNION/子查询/DDL

#### 2.1.3 元数据管理

在 `rx_config` 中存储 BPCS 表字段元数据（JSON 格式）：

```json
{
  "bpcs.report.tables": {
    "ECH": {
      "name": "订单头",
      "fields": {
        "CONO": {"label": "公司", "type": "string"},
        "ORNO": {"label": "订单号", "type": "string"},
        "CUST": {"label": "客户号", "type": "string"},
        "ORDTE": {"label": "订单日期", "type": "date"},
        "ORAMT": {"label": "订单金额", "type": "decimal"}
      }
    },
    "RCM": {
      "name": "客户主档",
      "fields": {
        "CONO": {"label": "公司", "type": "string"},
        "CUST": {"label": "客户号", "type": "string"},
        "CUNAME": {"label": "客户名称", "type": "string"}
      }
    }
  }
}
```

#### 2.1.4 安全约束

| 约束 | 说明 |
|------|------|
| 字段白名单 | 只能查询元数据中已注册的字段，禁止任意 SQL |
| 表白名单 | 只能查询 BPCS 只读表（ECH/ECL/RCM/IWI/IIM/LLH/BBH/SIH/SSH/HPH/HPO/ITL/ESH） |
| 禁止 UNION/子查询 | SQL 注入防护，只支持单表查询 + JOIN |
| 禁止 DDL/DML | 只允许 SELECT 语句 |
| 行数限制 | 预览 100 行，执行最多 10000 行 |
| 权限控制 | 需要 `BPCS_REPORT_BUILDER` 权限 |

## 四、SQL 注入防护说明

### 4.1 当前实现分析

当前 BPCS SQL 参数绑定采用**两层策略**，**已具备 SQL 注入防护能力**：

**第一层：库名拼接（受控）**

```xml
SELECT * FROM {lib}.ECH WHERE CONO = ? AND ORNO = ?
```

- `{lib}` 是库名占位符，在 Service 层通过 `.replace("{lib}", lib)` 替换
- 值来自 `rx_config(bpcs.library)`（默认 `BPCSF`）
- **安全措施**：替换前经过 `As400Identifiers.IDENTIFIER` 正则白名单校验（仅允许 `[A-Za-z0-9_/]`）
- SQL 标识符（库名/表名）无法通过 JDBC `?` 参数化，这是业界标准做法

**第二层：参数绑定（JDBC PreparedStatement）**

```xml
SELECT * FROM {lib}.RCM WHERE CONO = ? AND CUST LIKE ? AND CUNAME LIKE ? FETCH FIRST ? ROWS ONLY
```

- 所有用户输入值（CONO、ORNO、CUST、日期、LIKE 模式等）均通过 `?` 占位符
- 后端 `JTOpenSqlClient.executeQuery()` 使用 `PreparedStatement.setObject(i+1, params[i])` 绑定
- **零字符串拼接用户输入到 SQL**

### 4.2 是否需要改 XML 方式？

**不需要**。当前 XML 集中管理 SQL + `?` 参数绑定的方式是**最佳实践**：

| 对比项 | 当前方式（XML + ?） | 改为代码内联 |
|--------|---------------------|-------------|
| SQL 可维护性 | ✅ 集中管理，易修改 | ❌ 分散在各 Service 类 |
| SQL 注入防护 | ✅ JDBC PreparedStatement | ✅ 同样可用 PreparedStatement |
| 可读性 | ✅ SQL 与 Java 代码分离 | ❌ SQL 嵌在 Java 代码中 |
| 测试性 | ✅ 可独立测试 SQL 语法 | ❌ 需启动 Spring 容器 |

### 4.3 结论

**当前实现已安全，无需修改**。唯一需要关注的是 `{lib}` 库名拼接，已有白名单校验。如果要进一步增强，可以：

1. 增加库名白名单配置（`rx_config` 中允许的库名列表）
2. 在 `as400-bpcs.xml` 头部添加 SQL 注释说明安全约束
3. 增加 SQL 审计日志（记录每次查询的 SQL + 参数）
