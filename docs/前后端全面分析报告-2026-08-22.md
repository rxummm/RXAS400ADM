## 总体结论

项目整体质量高于平均水平：后端无 TODO 残留、SQL 全参数化、`@PreAuthorize` 覆盖率高、审计切面有敏感字段脱敏、前端有 8 道静态门禁 + 90 个单测。但存在 **1 个高危部署安全问题（JWT secret 默认值硬编码）**，以及前端 **2 个 CI 门禁当前红灯**（ESLint 13 error + i18n 2 个 key 缺失）。（零事务为 AGENTS.md §19.2 已决策的无事务架构，非缺陷，见 H1；docker-compose 明文/暴露已核实为 dev 脚本卫生，见 H2。）

**问题统计**：高危 5 项 / 中危 21 项 / 低危 24 项。

## 一、高危问题（P0，建议立即修复）

### H1. 零事务架构（已决策，非缺陷）【后端·架构说明】

依据 AGENTS.md §19.2，本项目为**无事务架构**：全库 0 个 `@Transactional`（已 Grep 验证），且 `scripts/check-transactional.sh` 门禁为**零容忍**（任何 `@Transactional` 含 rollbackFor 变体即失败，已接入 backend CI）。主数据源为 MySQL 8（InnoDB 单语句天然原子），AS400/DB2 for i 仅只读（QSYS2 + 命令执行），事务无收益，反而在 AS400 未开 Journaling 时引入 SQL7008 回滚静默失效风险。

原审计报告列为「全项目零事务管理，多表写操作无原子性」的 6 处写路径（`SysUserServiceImpl` 创建/更新角色、`RoleService.batchDelete`、`As400LoginService.applyRoles`、`PermissionRequestService.grantMenus`、`As400LoginSyncService` 定时任务）按当前架构属**预期行为**，不视为缺陷，不在整改范围。若未来将 AS400 立项为主写数据源，再按 §11.2 全量 32 表开启 Journaling 并重新评估事务策略。

旁证说明：`SysUserServiceImpl.java` 的 `@Override` 后孤立空行并非「历史删除事务注解痕迹」，而是既有代码风格，与零事务决策一致，不应据此推断曾存在事务注解。

### H2. docker-compose 明文口令/端口暴露 — 实为 dev 脚本卫生【部署·降级为 dev 卫生】

经核实，本项目**不使用 Docker 部署、也不使用 Redis**：代码库无任何 Redis 引用（仅 `RateLimitFilter.java:31` 一条未来建议注释），MySQL 才是唯一数据源；`docker-compose.yml` 只是本机联调起 MySQL 的便利脚本。原「部署·严重」定级对该项目实际部署不成立，降级为 dev 脚本卫生。

**已完成的整改（docker-compose.yml）**：
- 文件头标注 **DEV ONLY**，明确非生产部署物；
- **删除 redis 段**（死配置，无任何代码连接）；
- MySQL 口令改由 `env_file: .env` 注入，`.env` 已加入 `.gitignore`（含真实口令的变体不入库，提交 `.env.example` 占位）；
- `3306` 端口绑定 `127.0.0.1`，避免暴露到外部网卡；
- healthcheck 的 `-proot` 改为引用 `${MYSQL_ROOT_PASSWORD}` 环境变量。

**剩余建议（dev 卫生范畴，非安全风险）**：确保 `.env` 不被提交、compose 仅用于本机开发。

### H3. JWT secret 默认值硬编码进代码库【安全】

`application.yml:103`：`secret: ${RXAS400_JWT_SECRET:RXAS400-Enterprise-IBM-i-Operation-Platform-Secret-2026}`。虽有 `StartupGuard` 在非 mock 环境拒启兜底（设计好），但默认值已进 git 历史，mock/dev 环境可被伪造 token。

**修复**：改 `${RXAS400_JWT_SECRET:}` 空兜底 + StartupGuard 强校验（其机制已具备）。

### H4. profile 默认值不一致，fail-open【配置·严重】

未配置 `spring.profiles.active` 直接启动时行为自相矛盾：

| 组件 | 默认行为 | 位置 |
|---|---|---|
| SecurityConfig | 按生产处理 | `SecurityConfig.java:120` |
| GlobalExceptionHandler | 按生产处理 | `GlobalExceptionHandler.java:115` |
| CryptoConfig | **按 mock（开发密钥加密 AS400 密码）** | `CryptoConfig.java:50` |
| AS400ClientProviderImpl | **按 mock（全部走 Mock 客户端）** | `AS400ClientProviderImpl.java:52` |
| StartupGuard | 按 mock（跳过 JWT 密钥强校验，默认 `spring.profiles.active:mock`） | `StartupGuard.java:27` |

且 mock 判定逻辑（`anyMatch("mock")` / `activeProfile.contains("mock")`）在 5 处重复实现（SecurityConfig:120、GlobalExceptionHandler:115、CryptoConfig:50、AS400ClientProviderImpl:52、StartupGuard:39），未用 Spring `@Profile`/`Environment.acceptsProfiles` 机制。

**修复（代码侧，可选）**：统一默认 profile 为 prod（fail-secure）；mock 判定收敛为单一 Bean；生产 DB 显式设置 `system.mock-mode-enabled=false`（StartupGuard 已支持该闸门）。

**为何可不改代码、仅补文档即可（已落地）**：本缺陷的运行期风险仅在「启动未显式设 profile / 漏设 `RXAS400_JWT_SECRET`」时触发；正确配置下（显式 `spring.profiles.active=prod` + 设强随机 `RXAS400_JWT_SECRET`）5 处判定全部一致走 prod，风险不复现。且数据获取机制本身与 profile 的对应关系是**代码固定**的，与是否修这 5 处重复无关：

- **mock 档** → `AS400ClientProviderImpl` 返回 `MockAS400Client`，AS400（job/spool/对象/QSYS2/命令）走**假数据**；菜单/用户/角色/权限等仍读**真实 MySQL**（docker 或生产库），不受 profile 影响。
- **prod 档** → 返回 `JTOpenAS400Client`，AS400 走**真实 IBM i（JT400）**连接。

即 profile 只切换「AS400 这一层」的假/真，MySQL 数据源始终不变。实际生产部署脚本已正确：`scripts/start-backend.sh:36` 内置 `--spring.profiles.active=prod` 并自动加载 `RXAS400_JWT_SECRET`，`scripts/rxas400-backend.service:14` 同为 prod。唯一缺口是 AGENTS.md 的快捷启动命令未带 profile——现已补全：本地加 `--spring.profiles.active=mock`、生产加 `--spring.profiles.active=prod` 且必须注入 `RXAS400_JWT_SECRET`（或直接使用 `scripts/start-backend.sh`）。

**结论**：改动文档/启动命令即可彻底消除 fail-open 口子，**不影响任何运行期数据获取方式**——本地开发 AS400 仍为假数据（与改动前一致），生产正确切真实 IBM i，MySQL 部分恒为真实库。代码侧的统一重构仅属可维护性改进，可排期、非安全必选项。

## 四、做得好的地方（无需改动）

## 十一、Tags 切换菜单重复请求问题分析（2026-08-22）

### 11.1 问题描述

用户反馈：前端打开多个菜单后，在 tags 上切换菜单时，是否会重新向后端发请求？期望的行为是：
- 第一次打开菜单 → 触发 API 请求加载数据
- tags 上切换到已打开的菜单 → **不触发**请求，直接显示缓存的数据
- 左侧菜单点击已打开的菜单 → **不触发**请求
- tags 右键「刷新」→ 触发请求重新加载

### 11.2 架构分析

**核心机制**：`layout/index.vue` 使用 `<keep-alive :include="tagsStore.cachedViews">`，只有 `cachedViews` 数组中的组件名才会被 keep-alive 缓存。

**缓存名单来源**：`tagsStore.cachedViews` 由 `visitedViews` 中带 `cacheName` 的标签同步而来。而 `cacheName` 仅在路由声明 `meta.cached: true` 时才会设置。

**路由分类**：

| 分类 | 路由数量 | 缓存行为 | 切换标签后果 |
|---|---|---|---|
| `meta.cached: true` | ~20 个（system/* + audit/docs/flowcharts） | keep-alive 缓存 | ✅ 不销毁，不重新请求 |
| **无 `meta.cached`** | **~25 个（核心业务页）** | **不缓存** | **❌ 销毁重建，触发 onMounted → fetchData()** |

### 11.4 问题根因

`meta.cached: true` 仅在 system/* 路由和少数页面（audit/docs/flowcharts）上声明，核心业务页面（jobs/assets/query/ifs 等）未声明此标志。导致：

1. 这些页面的标签创建时 `cacheName` 为 `undefined`
2. `tagsStore.cachedViews` 不包含这些组件名
3. `<keep-alive :include>` 不缓存这些组件
4. 切换标签时 Vue 销毁当前组件、创建新组件
5. 新组件触发 `onMounted` → `fetchData()` → 向后端发请求

### 11.5 修复方案

**方案 A：为所有页面启用 keep-alive 缓存（推荐）**

1. **路由声明 `meta.cached: true`**（让 tagsStore 知道要缓存）
2. **组件声明 `defineOptions({ name: 'XxxPage' })`**（让 keep-alive 通过组件名匹配缓存）

| 步骤 | 操作 | 涉及文件 |

| 1 | 给 25 个非 cached 路由加 `meta: { ..., cached: true }` | `router/index.ts` |
| 2 | 给 25 个组件加 `defineOptions({ name: 'XxxPage' })` | 各 `views/**/*.vue` |
| 3 | 确保组件 name 与路由 name 或 cacheName 一致 | 对照表见下方 |
