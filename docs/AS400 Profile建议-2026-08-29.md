# AS400 业务增强建议 - 2026-08-29

## 需求概述

1. CL命令黑名单是否可以由管理员在前端配置（指定命令和用户名/AS400工号）
2. 实现单独的AS400 profile创建和修改页面，不放在可执行的CL命令里
3. 创建AS400 profile的页面需要分步执行（时间轴形式）

## 二、需求可行性评估

### 2.1 CL命令黑名单按用户/工号配置

**评估结论：不建议修改现有黑名单机制**

#### 原因分析：

1. **安全基线原则**：
   - CRTUSRPRF、DLTUSRPRF等命令是高危操作，应全局禁止
   - 安全策略应由代码版本控制，不应由运行时配置动态调整
   - 按用户放开权限会增加误操作和安全风险

2. **架构设计初衷**：
   - 现有黑名单设计是**全局安全策略**，不是权限控制
   - 权限控制应通过`@PreAuthorize`注解和权限码实现
   - CL命令黑名单是最后一道防线，不应被绕过

3. **替代方案更优**：
   - AS400 profile创建应走**专用接口**，不走通用CL命令执行通道
   - 专用接口可以做更细粒度的权限控制和审计

#### 如果确实需要按用户配置：

**建议方案**：在`rx_config`表新增配置键

```sql
-- 新增：允许执行CRTUSRPRF的用户列表（逗号分隔）
INSERT INTO rx_config (config_key, config_value, description)
VALUES ('cl.blacklist.allow-crtusrprf-users', '', 
        '允许执行CRTUSRPRF命令的用户列表(逗号分隔用户名)，为空则全局禁止');
```

**实现逻辑**：
- `DangerousClCommandValidator`新增用户白名单检查
- 从当前登录上下文获取用户名
- 如果用户在白名单中，跳过CRTUSRPRF检查

**但强烈不建议**，原因：
- CRTUSRPRF需要配套参数（密码、权限、描述等），通过CL命令执行参数复杂
- 缺乏审计追踪（不知道创建了什么用户）
- 无法做分步流程控制

### 2.2 AS400 Profile创建/修改页面

**评估结论：建议实现，且应走专用API而非CL命令**

#### 推荐架构：

```
前端（分步表单）
  ↓
后端专用API（/api/v1/as400/user-profiles/create）
  ↓
AS400 Service（封装JT400调用）
  ↓
JT400 API（ProgramCall 或 QSYS2视图）
  ↓
IBM i 系统
```

#### 技术选型：

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **方案A：QSYS2视图 + SQL** | 简单，可读性好 | 创建用户需要特殊权限，部分操作不支持 | ⭐⭐ |
| **方案B：ProgramCall调用系统函数** | 功能完整，可执行所有操作 | 需要了解IBM i系统API | ⭐⭐⭐⭐ |
| **方案C：CL命令封装** | 实现简单 | 受黑名单限制，参数复杂 | ⭐ |

**推荐方案B**：通过ProgramCall调用IBM i的用户管理API

### 3.4 后端Service实现

#### 3.4.1 Service接口

```java

public interface UserProfileService {
    UserProfileDetailVO getUserProfile(String userName);
    List<UserProfileListRow> listUserProfiles();

    void updateUserProfile(String userName, UserProfileUpdateDTO dto);
    void deleteUserProfile(String userName);

```

#### 3.4.2 Service实现（调用JT400 ProgramCall）

```java
@Service
@RequiredArgsConstructor
public class UserProfileServiceImpl implements UserProfileService {
    
    private final AS400ClientProvider clientProvider;
    
    @Override
    public UserProfileCreateResult createUserProfile(UserProfileCreateDTO dto) {
        // 方案1：通过ProgramCall调用QTEMP/QCMDEXC执行CRTUSRPRF
        // 方案2：通过QSYS2.USER_INFO视图 + 特殊权限
        // 方案3：通过IBM i的User Space API
        
        String command = buildCreateCommand(dto);
        CommandResult result = clientProvider.current().execute(command);
        
        if (result.success()) {
            // 发送邮件通知（如果需要）
            if ("YES".equals(dto.emailNotification())) {
                sendNotificationEmail(dto);
            }
            return new UserProfileCreateResult(true, "创建成功", 
                dto.userName(), Instant.now());
        }
        return new UserProfileCreateResult(false, result.message(), 
            dto.userName(), Instant.now());
    }
    
    private String buildCreateCommand(UserProfileCreateDTO dto) {
        StringBuilder cmd = new StringBuilder("CRTUSRPRF");
        cmd.append(" USRPRF(").append(dto.userName()).append(")");
        cmd.append(" PASSWORD(").append(dto.password()).append(")");
        cmd.append(" TEXT('").append(dto.description()).append("')");
        cmd.append(" SPCAUT(").append(
            String.join(" ", dto.specialAuthorities())).append(")");
        // ... 其他参数
        return cmd.toString();
    }
}
```

## 四、关于是否修改CL命令黑名单的建议

### 4.1 结论：**不需要修改现有黑名单机制**

#### 理由：

1. **功能分离原则**：
   - CL命令黑名单 = 安全基线（全局禁止高危命令）
   - AS400 Profile管理 = 业务功能（专用接口）
   - 两者职责不同，不应耦合

2. **安全最佳实践**：
   - 高危操作（CRTUSRPRF）应通过**专用受控接口**执行
   - 专用接口可做：参数校验、权限控制、审计日志、流程控制
   - 通用CL命令执行通道应保持最小权限原则

3. **审计追溯需求**：
   - 通过CL命令执行，审计日志只记录"执行了CRTUSRPRF"
   - 通过专用API，审计日志可记录：创建了谁、谁创建的、参数是什么、结果如何

### 4.2 如果用户坚持需要按用户配置黑名单

**妥协方案**：在`DangerousClCommandValidator`中增加白名单逻辑

```java
// 新增配置键
private static final String ALLOW_USERS_KEY = "cl.blacklist.allow-crtusrprf-users";

public void assertAllowed(String command, String currentUser) {
    Snapshot snap = currentSnapshot();
    if (!snap.enabled()) return;
    
    String verb = firstVerb(command);
    if (verb.isEmpty()) return;
    
    // 检查是否在白名单中
    if ("CRTUSRPRF".equals(verb) && isUserInAllowList(currentUser, snap)) {
        return; // 放行
    }
    
    // 原有黑名单检查逻辑...
}
```

**但这不推荐**，因为：
- CRTUSRPRF需要复杂参数，通过CL命令执行不友好
- 缺乏参数校验和审计
- 无法做分步流程控制

## 五、实施建议

### 5.1 优先级排序

| 优先级 | 功能 | 工作量 | 价值 |
|--------|------|--------|------|
| P0 | AS400 Profile创建页面（时间轴） | 5天 | 高 |
| P1 | AS400 Profile修改页面 | 2天 | 中 |
| P2 | AS400 Profile详情查看 | 1天 | 低 |
| P3 | 按用户配置黑名单（可选） | 2天 | 低 |

### 5.2 技术风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| JT400 ProgramCall权限不足 | 无法创建用户 | 确保连接用户有*SECADM权限 |
| CRTUSRPRF参数复杂 | 实现困难 | 参考IBM i文档，封装常用参数 |
| 邮件发送失败 | 通知不到用户 | 优雅降级，记录日志，允许重试 |

### 5.3 测试要点

1. **功能测试**：
   - 创建用户成功/失败场景
   - 修改用户信息
   - 删除用户
   - 邮件通知发送

2. **安全测试**：
   - 无权限用户访问（应返回403）
   - 参数注入攻击（如用户名含特殊字符）
   - 重复创建同名用户（应拒绝）

3. **集成测试**：
   - 前端页面完整流程
   - 后端API调用
   - 邮件发送集成

## 七、总结

1. **CL命令黑名单**：保持现有机制，不需要修改。高危命令应全局禁止，AS400 Profile创建走专用接口。

2. **AS400 Profile创建**：建议实现专用API + 前端时间轴向导，不走通用CL命令执行通道。

3. **技术方案**：推荐使用JT400 ProgramCall调用IBM i系统API，复用现有邮件模块发送通知。

4. **安全考虑**：通过`@PreAuthorize`控制权限，通过`@OperateLog`记录审计日志，通过专用接口做参数校验。
