## 十一、Flyway 迁移文件优化建议

### 11.1 现状分析

当前项目共有 **113 个** Flyway 迁移文件（V1~V112），存在以下问题：

| 问题 | 说明 |
|------|------|
| 文件数量多 | 113 个 SQL 文件，维护成本高 |
| 版本跳跃 | 历史上存在版本重复（V60/V61/V100），已修复为 V61/V102/V103 |
| 命名不统一 | 部分使用中文，部分使用英文 |
| 缺少聚合视图 | 没有统一的基线版本供新项目使用 |

### 11.2 优化方案

#### 方案一：创建基线版本（推荐）

**思路**：创建一个从 V1 开始的"聚合迁移文件"，包含所有当前表的 DDL，然后删除旧文件。

**实施步骤**：

1. **导出当前数据库结构**
   ```bash
   mysqldump -uroot -proot --no-data rxas400adm > schema_dump.sql
   ```

2. **创建基线迁移文件**
   ```sql
   -- V1__baseline_all_tables.sql
   -- 包含所有现有表的 CREATE TABLE 语句
   -- 不包含数据（数据通过后续迁移文件补充）
   ```

3. **在数据库中标记基线版本**
   ```sql
   INSERT INTO flyway_schema_history 
   (installed_rank, version, description, type, script, checksum, installed_by, installed_on, execution_time, success)
   VALUES (1, '1.0', 'baseline', 'SQL', 'V1__baseline_all_tables.sql', 0, 'root', NOW(), 0, 1);
   ```

4. **重命名现有迁移文件**
   - 将 V101~V112 重命名为 V2~V13
   - 或删除 V1~V100（如果已包含在基线中）

5. **清理历史迁移文件**
   - 备份后删除 V1~V100
   - 保留 V101~V112（重命名后为 V2~V13）

**优点**：
- 新项目可以直接从 V1 开始
- 减少迁移文件数量（从 113 个减少到 ~15 个）
- 便于版本管理和回溯

**缺点**：
- 需要停机维护
- 生产环境需要谨慎操作
- 需要保留历史迁移文件作为备份

---

#### 方案二：保留历史，新增聚合视图

**思路**：不删除现有迁移文件，而是创建视图或存储过程来聚合查询。

**实施步骤**：

1. **创建视图**
   ```sql
   CREATE VIEW v_all_tables AS
   SELECT TABLE_NAME, TABLE_COMMENT 
   FROM information_schema.TABLES 
   WHERE TABLE_SCHEMA = 'rxas400adm';
   ```

2. **创建文档化索引**
   - 维护一个 `MIGRATION_INDEX.md` 文件
   - 记录每个迁移文件的用途和变更内容

**优点**：
- 不需要修改现有迁移文件
- 保持历史可追溯性
- 实施风险低

**缺点**：
- 文件数量没有减少
- 维护成本仍然存在

---

#### 方案三：版本分组管理

**思路**：将迁移文件按业务模块分组，每组一个聚合文件。

**分组建议**：

| 组名 | 文件范围 | 内容 |
|------|---------|------|
| core | V1~V50 | 核心表结构 |
| bpcs | V51~V80 | BPCS 业务相关 |
| operation | V81~V100 | 运维功能相关 |
| business | V101~V112 | 新增业务模块 |

**实施步骤**：

1. **创建聚合文件**
   ```
   migration/
   ├── core/
   │   └── V1__core_tables.sql
   ├── bpcs/
   │   └── V2__bpcs_tables.sql
   ├── operation/
   │   └── V3__operation_tables.sql
   └── business/
       ├── V4__quality.sql
       ├── V5__cost.sql
       └── ...
   ```

2. **更新 Flyway 配置**
   ```yaml
   flyway:
     locations:
       - classpath:db/migration/core
       - classpath:db/migration/bpcs
       - classpath:db/migration/operation
       - classpath:db/migration/business
   ```

**优点**：
- 便于模块化管理
- 新增模块只需添加对应组文件
- 保持历史可追溯性

**缺点**：
- 需要修改 Flyway 配置
- 文件数量没有显著减少

---

### 11.3 推荐方案

**推荐采用方案一（创建基线版本）+ 方案三（版本分组管理）的组合**：

1. **短期**：创建基线迁移文件 `V1__baseline_all_tables.sql`
2. **中期**：按业务模块分组管理迁移文件
3. **长期**：逐步清理历史迁移文件

### 11.4 风险评估

| 风险 | 等级 | 应对措施 |
|------|------|---------|
| 数据丢失 | 高 | 完整备份数据库 |
| 迁移失败 | 中 | 保留历史文件备份 |
| 生产停机 | 高 | 选择低峰期执行 |
| 版本冲突 | 中 | 测试环境先行验证 |

### 11.5 实施建议

1. **测试环境先行**：在测试环境验证迁移脚本
2. **保留备份**：保留所有历史迁移文件作为备份
3. **分步执行**：先创建基线，再逐步清理
4. **文档更新**：更新 MIGRATION_INDEX.md 文档
