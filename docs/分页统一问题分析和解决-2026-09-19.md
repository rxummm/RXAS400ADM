# BPCS 分页统一问题分析与解决方案

> 日期：2026-09-19  
> 背景：全量代码审查发现 AS400/BPCS 业务模块下 60+ 个端点存在分页缺陷

---

## 一、问题现象

### 1.1 前端报错（已有修复）

| 页面 | 报错 | 根因 |
|------|------|------|
| `bpcs-orderTemplate` | `rows is not iterable` / `reduce is not a function` / `data Expected Array got Object` | 后端返回 `PageResult{records,total}` 但前端按 `Array` 处理 |
| `bpcs-rma` | 同上 | 同上 |
| `bpcs-orderSchedule` | 同上 + 日期选择器过宽 | 同上 |
| `bpcs-orderChange` | 点查询无数据无提示 | `orno` 为必填但前端无校验 |

### 1.2 静默截断（数据丢失）

后端 `queryListCheckedBounded(sql, limit, cono)` 硬编码 limit，超出部分**静默丢弃**：

```java
// WmsService.java:120-121
List<Map<String, Object>> rows = clientProvider.current()
        .queryListCheckedBounded(sql, 100, cono);  // limit=100 硬编码
```

**影响范围**：所有使用 `queryListCheckedBounded` 的非分页端点，limit 值从 50 到 500 不等。

### 1.3 前端无分页

约 28 个 BPCS 列表页面没有 `AppPagination`，数据量由后端硬编码 limit 决定：
- 用户无法翻页查看全部数据
- 后端丢数据时前端无感知

## 三、解决方案

### 3.1 核心原则

> **所有返回列表数据的端点必须支持服务端分页，前端统一使用 `useSmartQueryTable` + `AppPagination`。**

### 3.2 后端改造

#### 3.2.1 新增/改造 Controller

为每个非分页端点创建 QueryDTO（或复用已有的），添加 `current`/`size` 参数：

```java
// 示例：WmsController 新增分页版本
@GetMapping("/summary-paged")
@PreAuthorize("hasAuthority('BPCS_WMS_VIEW')")
public ApiResponse<PageResult<BpcsWarehouseSummaryVO>> summaryPaged(
        BpcsWarehouseSummaryQueryDTO dto) {
    return ApiResponse.success(wmsService.warehouseSummaryPaged(dto));
}
```

#### 3.2.2 Service 层改造

将 `queryListCheckedBounded(sql, limit, cono)` 改为分页查询：

```java
// 改造前
List<Map<String, Object>> rows = clientProvider.current()
        .queryListCheckedBounded(sql, 100, cono);

// 改造后
int offset = (dto.getCurrent() - 1) * dto.getSize();
String countSql = "SELECT COUNT(*) FROM (" + originalSql + ")";  // 先查总数
long total = clientProvider.current().queryScalarChecked(countSql, cono);
List<Map<String, Object>> rows = clientProvider.current()
        .queryListCheckedBounded(sql, dto.getSize(), cono);  // 带 offset 的分页查询
return new PageResult<>(total, rows.stream().map(this::toVO).toList());
```

#### 3.2.3 SQL 改造

在 SQL 末尾添加 `OFFSET ? ROWS FETCH FIRST ? ROWS ONLY`（DB2 for i 语法）：

```sql
-- 改造前
SELECT ... FROM {lib}.BIN WHERE CONO = ? GROUP BY ... ORDER BY ...

-- 改造后（加总数查询 + 分页）
-- countSql:
SELECT COUNT(*) FROM (
    SELECT BIN.WHSE FROM {lib}.BIN WHERE CONO = ? GROUP BY BIN.WHSE
) t

-- dataSql:
SELECT ... FROM {lib}.BIN WHERE CONO = ? GROUP BY ... ORDER BY ...
OFFSET ? ROWS FETCH FIRST ? ROWS ONLY
```

### 3.3 前端改造

#### 3.3.1 API 类型更新

```typescript
// 改造前
export const listLocations = (cono = '001', limit = 100) =>
  request.get<LocationInventory[]>('/bpcs/location/list', { params: { cono, limit } })

// 改造后
export const listLocations = (params?: { cono?: string; keyword?: string; current?: number; size?: number }) =>
  request.get<PaginatedResult<LocationInventory>>('/bpcs/location/list', { params })
```

#### 3.3.2 页面迁移模板

所有列表页面统一迁移到 `useSmartQueryTable` + `AppPagination`：

```vue
<template>
  <div class="page-container page-container--fit">
    <div class="search-bar">
      <el-input v-model="keyword" clearable @keyup.enter="forceSearch" />
      <el-button type="primary" @click="forceSearch">{{ $t('common.search') }}</el-button>
      <el-button @click="resetSearch">{{ $t('common.reset') }}</el-button>
    </div>
    <div class="table-wrapper">
      <el-table :data="tableData" v-loading="loading" size="small" border>
        <!-- 列定义 -->
      </el-table>
      <AppPagination v-model:current="current" v-model:size="size" :total="total"
                     @change="handlePageChange" @size-change="handleSizeChange" />
    </div>
  </div>
</template>

<script setup lang="ts">
import { useSmartQueryTable } from '@/composables/useSmartQueryTable'

const { tableData, keyword, loading, total, current, size,
        forceSearch, resetSearch, handlePageChange, handleSizeChange } = useSmartQueryTable<RowType>({
  fetchApi: (params) => listXxx({ ...customParams, current: params.current, size: params.size }),
  frontendPage: false,  // 后端分页
  searchFields: ['field1', 'field2'],
})
</script>
```

## 五、分层策略

### 5.1 后端分页 vs 前端分页

| 策略 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| **后端分页** (`PageResult`) | 数据量大（>500 行）、持续增长 | 只传输当前页数据，节省带宽 | 需要后端改造 |
| **前端分页** (`frontendPage: true`) | 数据量小且有界（配置表、汇总统计） | 实现简单，无需改后端 | 全量加载，不适合大数据量 |

### 5.2 分页策略选择原则

```
数据量判断：
├── < 100 行且不会增长 → 前端分页（如 KPI 卡片、配置项）
├── 100~500 行 → 优先前端分页，后端改造后切后端分页
└── > 500 行或持续增长 → 必须后端分页
```

### 5.3 已改造端点的分页策略

| 端点 | 当前策略 | 改后端后 |
|------|---------|---------|
| `location/list` | 前端分页（limit 500） | 后端分页 |
| `replenishment/list` | 前端分页（limit 500） | 后端分页 |
| `stockValue/report` | 前端分页（limit 500） | 后端分页 |
| `wms/summary` | 无分页（limit 100） | 后端分页 |

## 六、注意事项

### 6.1 DB2 for i 分页语法

```sql
-- DB2 for i 支持 SQL:2008 标准分页
OFFSET ? ROWS FETCH FIRST ? ROWS ONLY

-- 注意：OFFSET 必须配合 ORDER BY 使用
-- FETCH FIRST 在 DB2 for i 7.2+ 支持
```

### 6.2 `queryListCheckedBounded` 改造

当前 `queryListCheckedBounded(sql, maxRows, params...)` 的实现：
- 设置 `statement.setMaxRows(maxRows)` 后执行查询
- **不会**自动添加 `OFFSET`/`FETCH FIRST`
- 需要在 SQL 层面手动添加分页子句

改造方案：
1. 新增 `queryListCheckedPaged(sql, offset, size, params...)` 方法
2. 或在 Service 层手动拼接分页 SQL

### 6.3 兼容性

- 旧的 `List` 返回端点保留（标 `@Deprecated`），新端点加 `-paged` 后缀
- 前端迁移完成后删除旧端点
- 分页参数使用项目约定的 `PageConstants.clampNum/clampSize`（MAX_PAGE_SIZE=100）

### 6.4 不需要分页的端点

以下端点因业务特性不需要分页（数据量由业务实体数量决定且有上界）：

| 端点 | 原因 |
|------|------|
| `GET /bpcs/kpi` | 6 个 KPI 指标卡 |
| `GET /bpcs/forecast` | 预测分析图表（单条聚合结果） |
| `GET /bpcs/cpfr` | 协作预测分析（单条聚合结果） |
| `GET /bpcs/orderReport` | 报表图表（本地 mock 数据） |
| `GET /bpcs/orderTracking` | 单个订单追踪（按 orno 查询） |
| `GET /bpcs/orderDetail` | 单个订单明细（按 orno 查询） |
| `GET /bpcs/customerOverview` | 单个客户 360 视图（按 cust 查询） |
| `GET /bpcs/orderCopy` | 订单复制操作（非列表） |

## 十一、分页统一方案建议（2026-09-20）

### 11.1 QueryBar 组件说明

**QueryBar 不是强制规范，是可选的高级组件**。

| 特性 | 手写 `<div class="search-bar">` | `<QueryBar>` 组件 |
|------|--------------------------------|-------------------|
| 关键词输入 + 搜索/重置按钮 | 需手动实现 | 内置 |
| 缓存状态提示（fromCache） | 无 | 内置 `el-tag` 浮层 |
| 数据刷新闪烁反馈 | 无 | 内置 `useFlash` + `flashTick` |
| 前端过滤空结果引导 | 无 | 内置 `localFilterEmpty` 提示 |
| 右侧操作按钮插槽 | 需手动加 `flex-1` + 插槽 | 内置 `#right` 插槽 |
| 代码量 | ~15 行 | ~5 行 |

**建议**：
- **新页面**：推荐使用 `QueryBar`，减少重复代码，自动获得缓存提示/闪烁反馈等 UX 增强
- **存量页面**：保持现有 `<div class="search-bar">` 写法，不强制迁移（除非重构时顺手改）
- **两种写法在样式上完全一致**（QueryBar 内部就是 `.search-bar`），不会造成视觉不统一

### 11.2 分页参数接收方式统一

#### 现状对比

| 方式 | 示例 | 优点 | 缺点 |
|------|------|------|------|
| **@RequestParam** | `page(int current, int size)` | 简单直接 | 需手动调 `clampNum/clampSize`，易遗漏 |
| **QueryDTO** | `@Valid BpcsItemQueryDTO query` | getter 自动钳制，筛选参数内聚 | 需定义 DTO 类 |

#### 建议方案

**分层策略：存量 @RequestParam 补钳制，新增模块用 QueryDTO**

```java
// 1. 存量端点：补齐 PageConstants 钳制（最小改动）
@GetMapping("/list")
public ApiResponse<List<VO>> list(
        @RequestParam(defaultValue = "1") int current,
        @RequestParam(defaultValue = "10") int size) {
    current = (int) PageConstants.clampNum(current);   // 新增
    size = (int) PageConstants.clampSize(size);         // 新增
    return ApiResponse.success(service.list(current, size));
}

// 2. 新增模块：使用 QueryDTO（推荐）
@GetMapping("/list")
public ApiResponse<PageResult<VO>> list(@Valid XxxQueryDTO query) {
    // QueryDTO getter 中已自动 clampNum/clampSize
    return ApiResponse.success(service.list(query));
}
```

```java
// QueryDTO 示例
public class XxxQueryDTO extends PageParam {
    private String keyword;
    
    @Override
    public int getCurrent() {
        return (int) PageConstants.clampNum(super.getCurrent());
    }
    
    @Override
    public int getSize() {
        return (int) PageConstants.clampSize(super.getSize());
    }
}
```

**理由**：
1. @RequestParam 方式改动成本低（每端点加 2 行），适合存量代码快速补齐
2. QueryDTO 方式更规范（筛选参数与分页参数内聚），适合新增模块
3. 不强制存量迁移，避免大规模重构风险

### 11.3 monitor 模块分页分析

| 页面 | 当前状态 | 数据来源 | 数据量评估 | 是否需要分页 |

### 11.4 分页策略决策树

```
需要分页吗？
├── 数据量 < 50 行且不会增长 → 不需要分页（KPI 卡片、配置项、单次报告）
├── 数据量 50~500 行 → 前端分页（frontendPage: true）
└── 数据量 > 500 行或持续增长 → 后端分页（PageResult）
    ├── AS400/DB2 for i 查询 → As400PaginationHelper.queryPaged()
    └── MySQL 查询 → MyBatis Plus Page 或手写 LIMIT/OFFSET
```
