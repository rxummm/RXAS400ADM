## 一、架构概览与目标

### 1.1 项目概述

RXAS400ADM 是一个 IBM i (AS400) 运维管理平台，采用 Spring Boot 3.3 (Java 17) 多模块 Maven + Vue 3 (TypeScript, Vite) 前后端分离架构。

**核心特性：**
- 多模块 Maven：`common / system / security / as400 / source / monitor / app`
- 前端：Vue3 + TypeScript + Vite + Element Plus + Pinia + vue-i18n
- 数据库：MySQL 8（开发环境）/ DB2 for i（生产环境）
- 认证：Spring Security 6 + JWT
- 实时推送：WebSocket STOMP

### 1.3 关键约束

- **数据库方案**：项目自身表迁移到 US400CND 的 Library RXADMIN 中，使用 DB2 for i 原生存储
- **JDK 要求**：IBM i 使用 PowerPC (ppc64le/ppc64) 架构，需下载专用 JDK 17
- **无事务架构**：项目不使用 Spring `@Transactional`，采用状态机管理业务一致性

## 三、数据库迁移与初始化

### 3.1 数据库方案

**推荐方案**：使用 `docs/init_rxadmin.sql` 替代 Flyway

**原因：**
1. V1~V44 迁移文件使用 MySQL 语法（AUTO_INCREMENT、ENGINE=InnoDB、DATETIME等）
2. 改写为 DB2 for i 语法工作量大（8-16小时）
3. `init_rxadmin.sql` 已包含完整的建表+数据初始化（1208行）
4. 生产环境表结构稳定后不再频繁变更

### 3.2 MySQL → DB2 语法对照表

| MySQL 语法 | DB2 for i 语法 |
|---|---|
| `AUTO_INCREMENT` | `GENERATED ALWAYS AS IDENTITY` |
| `ENGINE=InnoDB` | 删除（DB2 无引擎概念） |
| `DEFAULT CHARSET=utf8mb4` | 删除（DB2 使用 CCSID） |
| `DATETIME` | `TIMESTAMP` |
| `TEXT` | `CLOB` |
| `TINYINT` | `SMALLINT` |
| `IFNULL(a, b)` | `COALESCE(a, b)` |
| `NOW()` | `CURRENT_TIMESTAMP` |
| `GROUP_CONCAT(...)` | `LISTAGG(... ON OVERFLOW TRUNCATE)` |
| `LIMIT n OFFSET m` | `OFFSET m ROWS FETCH NEXT n ROWS ONLY` |

### 3.3 执行数据库初始化

### 4.3 创建启动脚本

**start.sh：**

```bash
#!/bin/sh
# ============================================================
# RXAS400ADM 启动脚本（US400CND）
# 路径：/QOpenSys/rxas400/start.sh
# ============================================================

# JDK 路径
JAVA_HOME=/QOpenSys/rxas400/jdk17
PATH=$JAVA_HOME/bin:$PATH

# 项目目录
APP_HOME=/QOpenSys/rxas400
JAR=$APP_HOME/rxas400adm-app-1.0.0-SNAPSHOT.jar
LOG_DIR=$APP_HOME/logs
PID_FILE=$APP_HOME/rxas400adm.pid

# 环境变量（从 .env 加载）
if [ -f $APP_HOME/.env ]; then
    . $APP_HOME/.env
fi

# 启动前硬校验：缺密钥直接拒绝启动
if [ -z "$RXAS400_JWT_SECRET" ] || [ -z "$RXAS400_CRYPTO_KEY" ]; then
    echo "FATAL: RXAS400_JWT_SECRET / RXAS400_CRYPTO_KEY 未在 .env 中设置" >&2
    exit 1
fi

export RXAS400_IFS_DOC_ROOT=${RXAS400_IFS_DOC_ROOT:-/QOpenSys/rxas400/document}
export RXAS400_PORT=${RXAS400_PORT:-8080}
export RXAS400_LOG_DIR=$LOG_DIR
export SCHEDULING_POOL_SIZE=${SCHEDULING_POOL_SIZE:-3}

# 创建日志目录
mkdir -p $LOG_DIR

# 停止旧进程
if [ -f $PID_FILE ]; then
    OLD_PID=$(cat $PID_FILE)
    if kill -0 $OLD_PID 2>/dev/null; then
        echo "Stopping old process $OLD_PID..."
        kill $OLD_PID
        sleep 5
        if kill -0 $OLD_PID 2>/dev/null; then
            echo "Force killing $OLD_PID..."
            kill -9 $OLD_PID
        fi
    fi
    rm -f $PID_FILE
fi

# 启动应用
echo "Starting rxas400adm..."
nohup java \
    -Xms256m \
    -Xmx1024m \
    -Dfile.encoding=UTF-8 \
    -jar $JAR \
    --spring.profiles.active=prod,db2 \
    --server.port=$RXAS400_PORT \
    > $LOG_DIR/startup.log 2>&1 &

echo $! > $PID_FILE
echo "rxas400adm started, PID=$(cat $PID_FILE)"
echo "Log file: $LOG_DIR/startup.log"
echo "API URL: http://localhost:$RXAS400_PORT/api/v1"
```

### 4.6 从 mock 切换到正式环境

> 开发/演示阶段用 `mock` profile（AS400 走 `MockAS400Client` 假数据），上线必须切到 `prod`。

**切换机制总览：**

| # | 机制 | 位置 | mock 模式行为 | prod 模式行为 |
|---|------|------|--------------|--------------|
| 1 | Profile 判定 | `ProfileResolver.isMockMode()` | active profile 含 `mock` 即为真 | 不含 `mock` 一律按生产处理 |
| 2 | **默认值陷阱** | `application.yml` | `spring.profiles.active: mock` 是**默认值** | 启动命令**必须显式** `--spring.profiles.active=prod` 覆盖 |
| 3 | AS400 客户端切换 | `AS400ClientProviderImpl` | 每个"服务器"返回 `MockAS400Client` | 按 `rx_ibmi_system` 表记录 `new JTOpenAS400Client` |
| 4 | JWT 密钥强制 | `StartupGuard` | 无校验，允许内置默认密钥 | `RXAS400_JWT_SECRET` 未设置或等于内置默认值 → **拒绝启动** |
| 5 | 演示数据注入 | `DataInitializer` | 注入 admin/admin123、示例 IBM i 实例 | **全新空库直接拒启**；已有基础数据的库不注入 |

**切换前置条件：**

| # | 条件 | 验证方式 |
|---|------|---------|
| P1 | `rx_ibmi_system` 表已录入真实服务器（host/port/user/密码），且 `enabled=1` | 界面「服务器管理」 |
| P2 | 服务器密码是用**生产同一把 `RXAS400_CRYPTO_KEY`** 加密写入的 | 连通性验证 |
| P3 | 基础数据已初始化：角色/权限码/菜单/授权/admin 账号 | 按 `docs/init_rxadmin.sql` 执行 |
| P4 | `RXAS400_JWT_SECRET` 已设置为 ≥32 字节随机值 | `echo -n "$RXAS400_JWT_SECRET" | wc -c` ≥ 32 |
| P5 | CORS 已按前端实际访问来源调整 | 见配置项清单 |

## 十五、事务与状态机设计

### 15.1 为什么没有 MySQL 后，仍然存在"事务一致性问题"

即使：
```
MySQL ❌
DB2 for i ✅
```

仍然存在：
```
DB2 UPDATE
+
CL Command
+
IFS
+
Job
+
User Profile
+
Spool
```

这些操作并不是天然组成一个业务事务。

例如：
```
创建 IBM i 用户
```

可能执行：
```
① INSERT RX_USER_OPERATION
② CRTUSRPRF
③ CHGUSRPRF
④ GRPUSRPRF
⑤ 设置 Special Authority
⑥ 写 Audit
```

即使全部运行在同一台 IBM i：
```
① DB2 SQL
```

和：
```
② CRTUSRPRF
```

仍然属于不同类型的操作。

所以：
```
DB2 Transaction
```

不能简单等同于：
```
IBM i Business Transaction
```

### 15.2 "不使用事务"并不意味着"不需要一致性设计"

> **不使用 Transaction Management，只代表不依靠数据库事务解决跨步骤业务一致性；并不代表可以忽略一致性。**

应该采用：

```
Transaction
     ↓
不作为主要一致性手段

State Machine
     ↓
作为业务过程控制中心

Operation Log
     ↓
记录每一步

Idempotency
     ↓
防止重复执行

Retry
     ↓
处理临时失败

Compensation
     ↓
处理不可恢复失败
```

### 15.3 状态机的核心不是 Status，而是 State + Step

建议不要只有：
```
status
```

而应该至少有：
```
operation_id
operation_type
status
current_step
target
request_data
result_data
error_code
error_message
retry_count
last_error_at
next_retry_at
created_by
created_at
updated_at
```

### 15.4 建议的统一状态

所有长流程统一使用：

```
REQUESTED
RUNNING
WAITING
RETRYING
SUCCESS
FAILED
PARTIAL_SUCCESS
CANCEL_REQUESTED
CANCELLED
```

**状态定义：**

- **REQUESTED**：操作已经创建，但还没有开始
- **RUNNING**：正在执行
- **WAITING**：等待外部条件
- **RETRYING**：正在进行失败恢复
- **SUCCESS**：全部步骤成功
- **FAILED**：不可继续或者达到最大重试次数
- **PARTIAL_SUCCESS**：部分步骤成功，无法自动恢复
- **CANCEL_REQUESTED**：用户请求取消
- **CANCELLED**：操作最终取消

### 15.5 状态机设计原则

**原则 1：每个状态都有明确含义**

不能：
```
FAILED
```

却不知道哪一步失败。

**原则 2：状态只能按照合法路径转换**

不能：
```
FAILED → SUCCESS
```

**原则 3：每一步都有唯一 Step Code**

例如：
```
CREATE_USER
SET_GROUP
SET_AUTHORITY
VERIFY_USER
```

**原则 4：Retry 从失败步骤继续**

**原则 5：每一步必须可审计**

**原则 6：高风险操作必须二次确认**

**原则 7：尽量实现幂等**

## 十六、IBM i 执行安全设计

### 16.1 统一 Operation 定义

建议建立统一的 IBM i Operation：


### 16.2 风险等级定义

```
READ
WRITE
DESTRUCTIVE
CRITICAL
BREAK_GLASS
```

**对应关系：**

| Operation | Risk |
|---|---|
| JOB_LIST | READ |
| USER_LIST | READ |
| IFS_READ | READ |
| USER_CREATE | WRITE |
| IFS_WRITE | WRITE |
| SPOOL_DELETE | DESTRUCTIVE |
| JOB_END | DESTRUCTIVE |
| USER_DELETE | CRITICAL |
| CHGSYSVAL | CRITICAL |
| END_SUBSYSTEM_IMMED | CRITICAL |
| RAW_CL | BREAK_GLASS |

### 16.3 风险等级对应策略

**READ：**
- 要求：Permission + Audit

**WRITE：**
- 要求：Permission + Validation + Audit

**DESTRUCTIVE：**
- 要求：Permission + Validation + Confirmation + Audit

**CRITICAL：**
- 要求：Special Permission + Confirmation + Reason + Audit
- 必要时：Approval + MFA

**BREAK_GLASS：**
- 要求：Break-glass Permission + Explicit Confirmation + Reason + Audit + Command Policy + Possibly Approval

### 16.4 Raw CL 安全边界

当前：
```
executeCommand()
```

属于非常强的能力。

建议架构：
```
Normal API
     ↓
Typed Operation
     ↓
Validation
     ↓
Policy
     ↓
JT400
```

Raw CL：
```
Raw CL
  ↓
BREAK_GLASS
  ↓
Strong Permission
  ↓
Confirmation
  ↓
Reason
  ↓
Audit
  ↓
JT400
```

### 16.5 Blacklist 不能作为唯一安全边界

当前项目：
```
DangerousClCommandValidator
```

这个设计有价值，但是：
> Blacklist 只能作为第二道防线。

更合理的是：
```
Allowlist
```

例如正常业务只允许：
```
DSPJOB
ENDJOB
WRKACTJOB
DSPUSRPRF
...
```

对于 Raw CL：
```
Break-glass
```

再进行更严格的命令策略。

### 16.6 *ALLOBJ 等 Special Authority 单独授权

当前项目允许类似：
```
*ALLOBJ
*SAVRST
```

作为 User Profile 特殊权限。

这是非常高风险的。

应该至少区分：
```

```

和：
```

```

例如：
```
*ALLOBJ
*SECADM
*IOSYSCFG
*SAVSYS
*JOBCTL
```

不能仅仅因为：
```

```

就全部允许。

### 16.7 高风险操作 Audit 必须记录更多内容

例如：
```
operation
user
server
target
operation_type
risk_level
request_data
before_state
after_state
result
error
timestamp
```

但是：
```
PASSWORD
TOKEN
SECRET
```

必须：
```
MASK / NEVER STORE
```

## 十七、备份与恢复

### 17.1 备份对象与频率

| 对象 | 方式 | 频率 | 说明 |
|------|------|------|------|
| RXADMIN Library | `SAVLIB LIB(RXADMIN) DEV(*SAVSYS)` 或 `SAVDEV` | 每日 | 全部业务表 |
| 应用 jar + 前端 dist | `SAV` / tar 到 IFS 备份目录 | 每次发版前保留旧版 | 回滚依赖 |
| start.sh / .env / Nginx conf | 纳入 IFS 备份目录 | 变更即备 | 配置漂移恢复 |
| **两把密钥** | 离线介质（保险柜/密码管理器） | 生成时一次，**永不离机** | 见下方红框 |
| IFS 文档目录 | `SAV` `/QOpenSys/rxas400/document` | 每周或按变更量 | 发布文档/附件 |

> 🔴 **密钥保管是备份体系中最关键的一项**：
> - `RXAS400_CRYPTO_KEY` 丢失 → `rx_ibmi_system` 中全部服务器密码无法解密，**所有真机功能瘫痪**且不可修复
> - `RXAS400_JWT_SECRET` 丢失 → 全员被登出（重新签发即可，损失小）
> - 两把 KEY 明文只允许存在于：生产 .env 文件 + 一份离线纸质/加密存储

## 十八、版本升级与回滚

### 18.1 标准升级流程

```bash
# ── 升级前 ──────────────────────────────────────
# 1. 执行一次手动备份（见 M5）
# 2. 记录当前 Flyway 版本：

/QOpenSys/rxas400/start.sh && tail -f logs/startup.log
```

### 18.2 前端升级注意

- 直接替换 `/QOpenSys/rxas400/ui/` 内容即可（Vite hash 文件名天然免缓存问题）
- **index.html 必须不缓存**：Nginx 对 `location /` 的 index.html 加 `add_header Cache-Control "no-cache";`

### 18.3 回滚规则

| 场景 | 处置 |
|------|------|
| 新版启动失败（未执行迁移就挂了） | 换回旧 jar 重启即可，零残留 |
| 已成功执行新迁移后发现功能问题 | **禁止直接换旧 jar 了事**——DB schema 可能新于旧代码。评估二选一：<br>a) 若新迁移仅加列/加索引（向后兼容）：旧 jar 可直接跑<br>b) 若有破坏性 DDL：还原 M5 备份的 Library 至升级前状态再回滚 jar |
| 只想回滚前端 | 恢复 `ui.tgz` 备份 |

> 规范保障：本项目门禁要求**历史迁移文件永不修改**（prod `validate-on-migrate=true` 会拦截 checksum 漂移），新增变更一律新 V{n}，因此正常升级路径始终是安全的纯增量。

## 二十、多节点部署

> 当前代码已具备多节点基础：Quartz JDBC JobStore 集群 + 监控采集分布式锁。扩展前逐项核对下表。

### 20.1 各组件多节点行为矩阵

| 组件 | 互斥机制 | 多节点行为 | 需要的配置 |
|------|---------|-----------|-----------|
| Quartz 作业/报表调度 | ✅ JDBC JobStore 集群 | 同一任务只会被一个节点触发 | 两节点必须连**同一数据库** |
| 监控采集 CollectorScheduler | ✅ `rx_dist_lock` 表锁 | 抢到锁的节点采集 | 每个节点都设 `RXAS400_SCHEDULER_LOCK=true` |
| 告警升级 AlertUpgradeService | ✅ 抢占式置位 | 同批告警只会被一个节点处理 | 严格互斥已内置 |
| Token 黑名单清理等杂项 @Scheduled | ➖ 幂等删除/清理 | 双跑无副作用 | 无需处理 |
| HTTP 流量 | — | Nginx `upstream` 轮询两个节点 | `X-Forwarded-For` 透传链路保持 |
| WebSocket STOMP | — | simple broker 为**节点内存态** | 双节点需粘性会话（`ip_hash`） |

### 20.2 第二个节点上线步骤

```bash
# 0. 前提：节点 1 正常运行（QRTZ_ 表已初始化）
# ⚠️ 不要两节点同时做首次冷启动

# 1. 节点 2 部署相同 jar + 相同 .env

# 2. 节点 2 设置采集锁
export RXAS400_SCHEDULER_LOCK=true

# 3. Nginx upstream 化
upstream rxas400_backend {
    ip_hash;                       # WebSocket 粘性会话
    server 192.168.1.100:8080;     # 节点 1
    server 192.168.1.101:8080;     # 节点 2
}
# proxy_pass http://rxas400_backend;

# 4. 验证：停掉节点 1 → 调度任务在节点 2 正常触发
```

### 20.3 何时值得上双节点

| 场景 | 建议 |
|------|------|
| 纯高可用（防单点宕机） | ✅ 收益明确，按上述步骤 |
| 性能扩容 | ❌ 本系统瓶颈通常在 IBM i 单机，双节点不提升 AS400 侧吞吐 |
| 灰度发布 | ❌ 当前无服务注册发现，直接整节点切换更简单可控 |
