## 一、基于 SCOR 模型的供应链全景分析

## 二、订单全流程增强建议（详细）

### 2.1 订单全链路状态追踪（P1-P4 全流程）
BPCS 订单从创建到开出发票的全流程分为 P1-P4 四个阶段，当前项目已实现 ECH 表的基本查询，但缺乏对订单全流程状态的主动监控和问题检测。
**订单全流程状态节点**：
P1: 订单录入 → 信用检查 → 价格确认 → 库存分配
P2: 拣货单生成 → 仓库拣货 → 包装确认 → 发运
P3: 运输中 → 到达客户 → 签收确认
P4: 发票生成 → 发票打印 → 客户对账 → 收款核销
**P1 阶段（订单录入）问题检测**：
- 信用 Hold（CRHOLD）：客户信用额度不足，订单被自动 Hold，需人工审批
- 价格 Hold（PRHOLD）：特殊价格需要经理审批
- 发运 Hold（SHPHOLD）：发货地址问题或其他原因导致发货被 Hold
- 信用冻结：客户付款逾期超过 90 天，系统自动冻结
**P2 阶段（拣货发运）问题检测**：
- 库存不足分配：订单行无法全部分配，产生 Backorder
- 拣货延迟：超过承诺发货时间仍未拣货完成
- 替换物料：原物料库存不足，使用替代物料发货
**P3 阶段（运输交付）问题检测**：
- 签收差异：客户签收数量与发货数量不符
- 运输延迟：超过预计送达时间仍未签收
- 货损：运输过程中货物损坏
**P4 阶段（发票收款）问题检测**：
- 发票延迟：已发货但超过 3 天未生成发票
- 价格差异：发票金额与订单金额不一致
- 收款逾期：发票已开但超期未收款

### 2.2 建议⑨：异常检测引擎（P0 — 最高优先级）
**核心功能**：从被动查询变为主动监控。
- 每天自动扫描 ECH/ECL 表中处于异常状态的订单
- 异常类型包括：信用 Hold、缺货 Hold、价格 Hold、发货延迟、开票延迟
- 通过 WebSocket 实时推送到前端通知栏
- 在订单列表页用不同颜色标签标识异常状态
- 异常归类统计：哪些类型的异常最多？哪些客户经常异常？
**涉及 BPCS 表**：
- ECH（订单头）：含 SHPHOLD、CRHOLD、PRHOLD 等 Hold 标志字段
- ECL（订单行）：含分配数量、发运数量、订购数量

### 2.3 建议⑩：履行率与 Backorder 分析（P0）
**核心功能**：
- 订单履行率（Order Fill Rate）：已发运行数 / 总行数
- 行履行率（Line Fill Rate）：已发运数量 / 订购数量
- Backorder 分析：哪些物料经常缺货？哪些客户受影响最大？
- 趋势图：月度履行率趋势
**涉及 BPCS 表**：ECL（QTYO 订购数量、QTYS 发运数量）、ECH（订单头）

### 2.4 建议⑬：交期绩效 OTD（P0）
**核心功能**：
- 按客户、按物料、按销售员的 OTD 计算
- 提前、准时、延迟的分布统计
- 延迟原因归类（库存不足、生产延迟、运输延迟）
- OTD 趋势图
**涉及 BPCS 表**：ECH（ORDDTE 订单日期、RQSDTE 要求日期）、ESH（SHIPDTE 实际发运日期）

### 2.5 建议⑰：订单详情信息增强（P0）
**核心功能**：在现有订单详情页基础上增加：
- 行的完整状态标签（已分配 / 部分发运 / 全部发运 / 已开票 / 已取消）
- 行的分配明细（从哪个仓库、哪个库位分配）
- 行的发运追踪（关联的发运号和运单号）
- 行的发票信息（关联的发票号和金额）
- 订单历史事件时间线
**涉及 BPCS 表**：ECL（订单行）、ESH（发运行）、EIN（发票关联）

### 2.6 建议⑳：客户 360° 视图（P0）
**核心功能**：在一个页面集中展示客户全方位信息：
- 客户基本信息（来自 RCM 表）
- 信用额度、已用额度、可用额度
- 最近 12 个月的订单趋势
- 当前未结订单列表
- 逾期发票列表
- OTD 绩效
- 退货/投诉记录
**涉及 BPCS 表**：RCM（客户主文件）、ECH（订单头）、EIN（发票头）

### 2.7 建议⑯：订单看板视图（P2）
**核心功能**：用 Kanban 风格展示订单流动：待处理 → 分配中 → 发运中 → 已完成

### 2.8 建议⑱：拣货分配可视化（P1）
**核心功能**：展示每个仓库的待拣货订单列表，支持按优先级排序，按库位分组。

### 2.9 建议⑮：订单审计时间线（P2）
**核心功能**：记录每个订单的关键事件时间线：订单创建 → 信用检查 → 库存分配 → 拣货单打印 → 发运确认

### 3.3 建议㉙：循环盘点支持（P0）
**背景**：制造业库存管理中最基础也最重要的环节。没有准确的库存数据，所有供应链决策都不可靠。
**具体功能**：
- ABC 分类盘点频率：A 类每月、B 类每季度、C 类每半年
- 盘点计划生成：每天 N 个物料，确保在一个周期内覆盖所有物料
- 盘点录入：仓库人员录入实盘数量，系统自动计算差异
- 差异分析：差异数量、差异金额、差异百分比、差异原因归类
- 盘点报告：月度盘点报告，含盘点覆盖率、准确率、差异汇总
**涉及 BPCS 表**：IWI（库存，读取盘点前库存）、ITL（交易，记录盘点调整）
**MySQL 新增表**：
- rx_cycle_count_plan（盘点计划）：计划编号、物料、仓库、计划日期、状态
- rx_cycle_count_result（盘点结果）：关联计划、实盘数量、系统数量、差异、原因、盘点人

### 3.4 建议㉛：呆滞物料专项分析（P0）
**背景**：呆滞物料占用大量资金和仓储空间，是制造业库存管理的核心痛点。
**具体功能**：
- 呆滞判定规则：3 个月无交易（潜在呆滞）、6 个月无交易（呆滞）、12 个月无交易（死库存）
- 呆滞物料清单：物料号、描述、在手量、库存价值、最后交易日期、呆滞天数
- 呆滞原因分析：工程变更、客户取消、采购过量、MOQ 过高
- 呆滞处理建议：退货给供应商、调拨、降价促销、报废
- 呆滞趋势图：月度呆滞金额变化趋势
**涉及 BPCS 表**：IWI（库存量）、IIM（物料主文件）、ITL（交易历史，判断最后交易日期）

### 3.5 建议㉗：库位库存可视化（P1）
**核心功能**：按仓库 → 库位 → 物料的三级下钻，展示每个库位的库存分布。

### 3.6 建议㉘：交易流水增强（P1）
**核心功能**：在现有 ITL 交易流水基础上增加：
- 交易类型中文标签（收货、发货、盘点调整、移库、退货）
- 关联单据号（关联的 PO/SO/盘点单号）
- 交易时间轴视图
- 按物料维度的交易汇总

### 3.7 建议㉜：预警规则引擎升级（P1）
**核心功能**：将现有硬编码的安全库存预警升级为可配置的规则引擎：
- 支持多种预警类型（低库存、高库存、呆滞、无交易）
- 支持按仓库、按物料类别、按供应商配置规则
- 支持预警阈值可配置
- 支持预警通知方式（站内通知、邮件）

### 3.8 建议㊲：ABC/XYZ 矩阵分析（P1）
**背景**：单一 ABC 分类（按价值）只能回答"哪些物料最值钱"，但不能回答"哪些物料最难预测"。制造业最佳实践是使用 ABC/XYZ 矩阵。
**XYZ 分类**：基于 SSH/ITL 历史数据，计算物料需求变异系数（CV）：
- X 类：CV < 0.5（需求稳定，如标准件）
- Y 类：0.5 ≤ CV ≤ 1.0（需求波动）
- Z 类：CV > 1.0（需求极不稳定，如定制件）
**矩阵展示（9 宫格）**：
|  | 需求稳定 (X) | 需求波动 (Y) | 需求极不稳定 (Z) |
|--|-------------|-------------|-----------------|
| **高价值 (A)** | AX：精准预测，JIT 补货 | AY：中等预测，定期补货 | AZ：高安全库存 |
| **中价值 (B)** | BX：定期补货 | BY：批量补货 | BZ：按需采购 |
| **低价值 (C)** | CX：看板/Kanban | CY：批量采购 | CZ：按需采购 |
**涉及 BPCS 表**：SSH（销售历史）、ITL（消耗历史）、IWI（库存价值）

### 3.9 建议㊿：库存多级一致性核对（P1）

#### 3.9.1 业务背景
BPCS 中库存数据分布在多个层级表中，同一 SKU 在 **托盘级（IPI）**、**库位级（ILI）**、**仓库级（IWM）** 分别维护库存数量。由于操作失误、系统延迟、数据同步异常等原因，三个层级的库存数量可能不一致，导致拣货分配错误、库存报表失真、盘点差异等问题。
**核心需求**：输入 SKU + 仓库代码，查出该物料在 Pallet Level（IPI）、Location Level（ILI）、Warehouse Level（IWM）各级别的库存数量，并自动对比是否存在差异。

#### 3.9.2 涉及 BPCS 表
| 表名 | 层级 | 说明 | 关键字段 |
|------|------|------|---------|
| **IPI**（Inventory Pallet Information） | Pallet 级 | 每个托盘/Pallet 上的库存数量 | WH（仓库）、ITEM（物料）、PALLET（托盘号）、QTY（数量） |
| **ILI**（Inventory Location Information） | Location 级 | 每个库位上的库存数量 | WH（仓库）、ITEM（物料）、LOCATION（库位）、QTY_ON_HAND（在手量） |
| **IWM**（Inventory Warehouse Master） | Warehouse 级 | 按仓库聚合的库存总量 | WH（仓库）、ITEM（物料）、PHY_STOCK_QTY（物理库存量） |

#### 3.9.3 核心功能
| 功能 | 说明 |
|------|------|
| 多级库存查询 | 输入 SKU + 仓库代码，查询该物料在 IPI/ILI/IWM 三个级别的库存量 |
| 一致性自动对比 | 自动计算三个级别的汇总数量，对比差异 |
| 差异标识 | 对不一致的层级用红色高亮标识，显示差异数量和差异百分比 |
| 差异明细下钻 | 点击差异数量，查看该层级的具体明细（如哪些库位/托盘有差异） |
| 历史趋势 | 记录每次查询结果，展示该物料多级库存差异的历史变化趋势 |

## 四、运输管理增强建议（详细）

### 4.1 制造业运输管理标准流程
订单发运 → 承运商选择 → 运单创建 → 调度装车 → 在途跟踪 → 签收确认 → 运费结算

### 4.2 当前项目发运管理现状
**已有**：
- 发运看板（LLH 表查看）— 载荷编号、承运商、目的地、发运日期
- 发运列表视图（LLH 表搜索）— 按载荷号、承运商搜索
- 订单全链路追踪（ESH 表）— 行级 SHIPDTE、SHSTAT 字段
**缺失（几乎全部）**：
- 运单管理（无运单号、追踪号）
- 承运商管理（无承运商档案、合同价）
- 在途跟踪（无状态更新）
- 签收管理（无 POD）
- 运费核算（无运费数据）
- 运输 KPI（无准时率、破损率）
- 运输单 PDF 打印（无单据打印功能）
- WABP 自动分货打单配置（无配置维护界面）

### 4.3 建议㊳：运单与发运执行管理（P1）
**核心功能**：
- 运单详情页：展示运单全貌（运单号、承运商、追踪号、发运日期、预计送达、关联订单）
- 运单状态跟踪：待发运 → 已装车 → 运输中 → 到达分拨中心 → 派送中 → 已签收 → 已关闭
- 批量运单操作：批量创建运单、批量打印面单、批量更新状态
- 运单导出：导出运单明细供物流对账
**涉及 BPCS 表**：LLH（载荷头，已有）、ESL/ESD（发运明细，需确认）
**MySQL 新增表**：
- rx_shipment（运单主表）：运单号、载荷号、承运商、追踪号、状态、发运日期、预计送达、实际签收
- rx_shipment_event（运单事件表）：时间、地点、事件类型、描述、操作员
- rx_shipment_line（运单明细表）：关联运单、物料号、数量、重量、包装类型

### 4.4 建议㊴：承运商管理与绩效评价（P1）
**核心功能**：
- 承运商档案：承运商名称、联系人、电话、合作级别、运输区域、合同价
- 承运商绩效评分卡：准时到达率、签收及时率、破损率、投诉率、综合评分
- 承运商对比：选择多个承运商并排对比
**涉及数据源**：LLH（承运商名称）、MySQL rx_carrier（承运商档案）、rx_shipment（运单绩效数据）

### 4.5 建议㊶：在途跟踪与签收管理（P1）
**核心功能**：
- 在途跟踪：运单详情页展示运输事件时间线，ETA 实时更新
- 签收管理（POD）：签收人、签收时间、签收方式、签收照片
- 异常签收处理：拒收、破损、部分签收
**涉及数据源**：MySQL rx_shipment（运单状态）、rx_shipment_event（事件）、rx_pod（签收记录）

### 4.6 建议㊵：运费核算与成本分析（P2）
**核心功能**：

- 运费核算：实际运费 vs 预估运费对比

### 4.7 建议㊷：运输管理仪表盘（P2）

### 4.8 建议㊼：运输单 PDF 打印（P1）

// 伪代码 - 核心渲染逻辑
public class WaybillPdfRenderer {
    public byte[] render(WaybillDataVO data) {
        Document doc = new Document(PageSize.A4);
        ByteArrayOutputStream out = new ByteArrayOutputStream();
        PdfWriter writer = PdfWriter.getInstance(doc, out);
        doc.open();
        // 1. 标题 + 运单号
        Font titleFont = new Font(Font.FontFamily.HELVETICA, 18, Font.BOLD);
        doc.add(new Paragraph("运 输 单", titleFont));
        doc.add(new Paragraph("运单号: " + data.getWaybillNo()));
        // 2. 发货方 / 收货方（两列）
        PdfPTable infoTable = new PdfPTable(2);
        infoTable.addCell(createInfoCell("发货方", data.getShipper()));
        infoTable.addCell(createInfoCell("收货方", data.getConsignee()));
        doc.add(infoTable);
        // 3. 承运商信息
        doc.add(new Paragraph("承运商: " + data.getCarrier()));
        doc.add(new Paragraph("发运日期: " + data.getShipDate()));
        // 4. 货物明细表
        PdfPTable itemTable = new PdfPTable(7);
        itemTable.addCell("序号"); itemTable.addCell("SKU");
        itemTable.addCell("品名"); itemTable.addCell("数量");
        itemTable.addCell("单位"); itemTable.addCell("重量");
        itemTable.addCell("体积");
        for (int i = 0; i < data.getItems().size(); i++) {
            WaybillItemVO item = data.getItems().get(i);
            itemTable.addCell(String.valueOf(i + 1));
            itemTable.addCell(item.getSku());
            itemTable.addCell(item.getDesc());
            itemTable.addCell(String.valueOf(item.getQty()));
            itemTable.addCell(item.getUom());
            itemTable.addCell(String.valueOf(item.getWeight()));
            itemTable.addCell(String.valueOf(item.getVolume()));
        }
        doc.add(itemTable);
        // 5. 合计
        doc.add(new Paragraph("合计: " + data.getSummary()));
        // 6. 签名区
        doc.add(new Paragraph("发货人签名: ___________"));

        return out.toByteArray();
    }
}

### 4.9 建议㊽：WABP 自动分货打单配置维护（P1）

#### 4.9.1 业务背景
BPCS 的 **WABP（Wave Auto Batching Parameters）** 表用于配置自动分货打单的参数，决定了仓库在发运作业时如何自动分波次、如何自动生成拣货单。当前项目没有 WABP 配置的维护界面，业务人员需要直接登录 AS400 绿屏修改参数，效率低且容易出错。
**核心需求**：实现 WABP 配置表的 CRUD 维护界面，支持根据仓库代码 + 星期几查询和修改配置，并可批量导入/导出配置。

#### 4.9.2 WABP 表结构（BPCS 原生）
| 字段名 | 类型 | 说明 | 示例值 |
|--------|------|------|--------|
| WH | CHAR(3) | 仓库代码 | WH1 |
| DAY_OF_WEEK | DEC(1) | 星期几（1=周一 ~ 7=周日） | 1 |
| TIME | TIME | 自动分货时间 | 14:00:00 |
| SHPHOLD | CHAR(1) | 是否处理发运 Hold 订单 | Y |
| CRHOLD | CHAR(1) | 是否处理信用 Hold 订单 | N |
| PRHOLD | CHAR(1) | 是否处理价格 Hold 订单 | N |
| ACTIVE | CHAR(1) | 启用标志 | Y |
| MAINT_USER | CHAR(10) | 维护人 | ADMIN |

### 4.10 建议㊾：RCMX 客户 CSR 分配管理（P1）

#### 4.10.1 业务背景
BPCS 中 **RCMX** 表用于维护客户与 Responsible CSR（Customer Service Representative，客户服务代表）的分配关系。在客户服务管理中，每个客户需要分配一个负责的 CSR，以明确客户服务责任归属、提升客户响应效率。
**业务规则**：
- 一个客户只能有一个 RESP CSR（唯一约束）
- 一个 CSR 可以负责多个客户（一对多关系）
- 支持 CSR 变更，变更后原 CSR 失去对该客户的管理权
- 支持启用/停用（ACTIVE flag），停用后客户不再有 CSR 负责

#### 4.10.6 唯一性约束
**业务规则**：一个客户只能有一个活跃的 RESP CSR。
**实现方式**：
- 新增时：检查该客户是否已有 ACTIVE='Y' 的记录，如有则提示"该客户已分配 CSR，请先停用现有分配"
- 变更时：将原记录的 ACTIVE 置为 'N'，新增一条 ACTIVE='Y' 的记录（或更新现有记录）
- 或者采用物理唯一约束：在数据库中保证 CUST 唯一，变更为直接 UPDATE

### 6.2 实施建议

#### 6.2.1 技术路线
| 层面 | 技术选型 | 说明 |
|------|---------|------|
| 后端框架 | Spring Boot（现有） | 复用现有项目架构 |
| AS400 数据访问 | AS400Client（现有） | 复用现有 JDBC 连接 |
| MySQL 新增表 | MyBatis-Plus（现有） | 新增业务表 |
| 前端框架 | Vue3 + Element Plus（现有） | 复用现有组件库 |
| PDF 生成 | OpenPDF（推荐）或 JasperReports | 轻量级/模板驱动 |
| Excel 处理 | Apache POI（现有依赖） | 导入导出 |
| 报表 | 现有 ECharts 图表 | 趋势图、仪表盘 |

#### 6.2.2 开发模式
- **后端**：Controller → Service → Mapper/SQL XML（遵循现有项目结构）
- **前端**：Vue 页面 → API 调用 → Element Plus 组件渲染（遵循现有项目结构）
- **数据**：BPCS 原生表直接 AS400 SQL 操作，新增业务表使用 MySQL MyBatis-Plus

#### 6.2.3 关键注意事项
1. **AS400 性能**：BPCS 表查询注意性能，避免全表扫描，使用 FETCH FIRST N ROWS ONLY 限制返回行数
2. **数据一致性**：直接操作 AS400 表时注意事务管理，更新操作建议使用 AS400 原生事务
3. **前端交互**：复杂交互（如 PDF 预览、批量导入）参考现有实现模式
4. **权限管理**：对 AS400 表的写操作（增删改）需要严格的权限控制，建议记录操作日志
5. **测试策略**：先在测试环境验证 SQL 语句，确认对 BPCS 表无负面影响后再上线

### 8.3 Top 5 详细实现方案
