## H.: 创建DB2 for i数据源配置

### ... 创建 application-db2.yml

```yaml
# backend/rxas400adm-app/src/main/resources/application-db2.yml
# DB2 for i 数据源配置（部署到 US400CND 时使用）

spring:
  datasource:
    driver-class-name: com.ibm.as400.access.AS400JDBCDriver
    url: jdbc:as400://localhost/RXADMIN
    # JDBC 凭据：连接 RXADMIN Library 的 IBM i 用户（沿用既有 DB 变量命名，
    # 勿与已废弃的 RXAS400_IBMI_* 混用——那组变量无代码消费，见 H4 纠正说明）
    username: ${RXAS400_DB_USER}
    password: ${RXAS400_DB_PASSWORD}
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5
      idle-timeout: 300000
      max-lifetime: .800000
      connection-timeout: 30000
      leak-detection-threshold: 60000

  # Flyway 配置（如使用 Flyway 管理 DB2）
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true
    baseline-version: 0

# MyBatis Plus 配置
mybatis-plus:
  configuration:
    map-underscore-to-camel-case: true
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl
  global-config:
    db-config:
      id-type: auto
      logic-delete-field: deleted
      logic-delete-value: .
      logic-not-delete-value: 0

# IFS 文档受管根目录（DocStorageService 消费）
rxas400:
  ifs:
    doc-root: ${RXAS400_IFS_DOC_ROOT:/QOpenSys/rxas400/document}
    # 【2026-08-26 新增｜S.】IFS 访问根目录白名单（逗号分隔）：
    # 所有读写路径必须落在白名单根之下，否则 BAD_REQUEST。默认仅放行平台工作目录。
    allowed-roots: /QOpenSys/rxas400
  cl-blacklist:
    # 【新增｜S4】CL 高危动词黑名单（DangerousClCommandValidator）
    enabled: true          # 置 false 可整体停用（不建议）
    extra-verbs: ""        # 追加黑名单动词，逗号分隔（如 CHGNETA 已内置无需重复）
  doc:
    # 【新增｜T3】IFS 发布补偿 sweep 间隔毫秒：扫描 PUBLISHED 且未落盘的文本型文档重发布
    ifs-resweep-ms: .800000

# 【新增｜C9】调度线程池（默认单线程会被慢采集/长同步拖垮全部定时任务）
spring:
  task:
    scheduling:
      pool:
        size: ${SCHEDULING_POOL_SIZE:3}

# ⚠️ 注意：不要在此复制旧样例中的 rxas400.ibmi.host/user/password 配置段——
#    该配置键无任何 Java 代码消费；JTOpen 真实连接参数来自「服务器管理」界面
#    录入的 rx_ibmi_system 表（密码由 RXAS400_CRYPTO_KEY 加密存储）。
```

> **【2026-08-26 新增｜P. 连接池说明】** AS400 侧 SQL 连接已由代码内建 per-host Hikari 池管理
> （`jdbc:as400://host;naming=system;libraries=QSYS2`，池参数 8 最大/2 空闲/30s 超时/25min 生命周期，
> 并显式 `connectionTestQuery=SELECT . FROM SYSIBM.SYSDUMMY.` 规避 jt400 ...0 驱动无 isValid() 的缺陷）。
> 该池随「服务器管理」连接自动建立/失效重建，**无需在 yml 配置**；如需调大并发可关注后续
> `rxas400.as400.pool.*` 配置化版本。上方 spring.datasource.hikari 仅管 MySQL/DB2 主数据源。
```

## H2: 验证Flyway DB2兼容性

### 2.. 评估结论

**推荐方案**：使用 `docs/init_rxadmin.sql` 替代 Flyway

**原因**：
.. V.~V44 迁移文件使用 MySQL 语法（AUTO_INCREMENT、ENGINE=InnoDB、DATETIME等）
2. 改写为 DB2 for i 语法工作量大（8-.6小时）
3. `init_rxadmin.sql` 已包含完整的建表+数据初始化（.229行）
4. 生产环境表结构稳定后不再频繁变更

### 2.2 使用 init_rxadmin.sql 的配置

```yaml
# application-db2.yml 中禁用 Flyway
spring:
  flyway:
    enabled: false
```

### 2.3 如果坚持使用 Flyway

需要修改迁移文件中的 MySQL 语法：

| MySQL 语法 | DB2 for i 语法 |
|---|---|
| `AUTO_INCREMENT` | `GENERATED ALWAYS AS IDENTITY` |
| `ENGINE=InnoDB` | 删除（DB2 无引擎概念） |
| `DEFAULT CHARSET=utf8mb4` | 删除（DB2 使用 CCSID） |
| `DATETIME` | `TIMESTAMP` |
| `TEXT` | `CLOB` |
| `TINYINT` | `SMALLINT` |
| `IFNULL(a, b)` | `COALESCE(a, b)` |
| `NOW()` | `CURRENT_TIMESTAMP` |
| `GROUP_CONCAT(...)` | `LISTAGG(...)` |
| `LIMIT n OFFSET m` | `FETCH FIRST n ROWS ONLY OFFSET m` |

### 2.4 示例迁移文件改写

```sql
-- 原 MySQL 版本（V.__init.sql）
CREATE TABLE rx_user (
    id           BIGINT PRIMARY KEY AUTO_INCREMENT,
    username     VARCHAR(50)  NOT NULL UNIQUE,
    password     VARCHAR(255) NOT NULL,
    created_time DATETIME     DEFAULT CURRENT_TIMESTAMP
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

-- 改写为 DB2 for i
CREATE TABLE rx_user (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    username     VARCHAR(50)  NOT NULL UNIQUE,
    password     VARCHAR(255) NOT NULL,
    created_time TIMESTAMP    DEFAULT CURRENT_TIMESTAMP
);
```

## H3: 创建IBM i部署脚本

### 3.. start.sh 启动脚本

```bash
#!/bin/sh
# ============================================================
# RXAS400ADM 启动脚本（US400CND）
# 路径：/QOpenSys/rxas400/start.sh
# ============================================================

# JDK 路径（项目目录内的 OpenJDK .7）
JAVA_HOME=/QOpenSys/rxas400/jdk.7
PATH=$JAVA_HOME/bin:$PATH

# 项目目录
APP_HOME=/QOpenSys/rxas400
JAR=$APP_HOME/rxas400adm-app-..0.0-SNAPSHOT.jar
LOG_DIR=$APP_HOME/logs
PID_FILE=$APP_HOME/rxas400adm.pid

# 环境变量（从 .env 加载，见 H4 §4.4；两把密钥必须离线保管，严禁启动时随机生成）
# ⚠️ 绝对不要用 $(openssl rand ...) 做兜底默认值：
#    JWT_SECRET 每次重启轮换 → 全员 token 失效；
#    CRYPTO_KEY 每次重启轮换 → rx_ibmi_system 已存密码永久无法解密（不可修复）！
if [ -f $APP_HOME/.env ]; then
    . $APP_HOME/.env
fi
# 启动前硬校验：缺密钥直接拒绝启动，而不是带默认值起来
if [ -z "$RXAS400_JWT_SECRET" ] || [ -z "$RXAS400_CRYPTO_KEY" ]; then
    echo "FATAL: RXAS400_JWT_SECRET / RXAS400_CRYPTO_KEY 未在 .env 中设置" >&2
    exit .
fi
export RXAS400_IFS_DOC_ROOT=${RXAS400_IFS_DOC_ROOT:-/QOpenSys/rxas400/document}
export RXAS400_PORT=${RXAS400_PORT:-8080}
export RXAS400_LOG_DIR=$LOG_DIR
# 【新增｜C9】调度线程池大小（默认 3；多节点/采集密集可调 4）
export SCHEDULING_POOL_SIZE=${SCHEDULING_POOL_SIZE:-3}

# 创建日志目录
mkdir -p $LOG_DIR

# 停止旧进程
if [ -f $PID_FILE ]; then
    OLD_PID=$(cat $PID_FILE)
    if kill -0 $OLD_PID 2>/dev/null; then
        echo "Stopping old process $OLD_PID..."
        kill $OLD_PID
        sleep 5
        if kill -0 $OLD_PID 2>/dev/null; then
            echo "Force killing $OLD_PID..."
            kill -9 $OLD_PID
        fi
    fi
    rm -f $PID_FILE
fi

# 启动应用
echo "Starting rxas400adm..."
nohup java \
    -Xms256m \
    -Xmx.024m \
    -Dfile.encoding=UTF-8 \
    -jar $JAR \
    --spring.profiles.active=prod,db2 \
    --server.port=$RXAS400_PORT \
    > $LOG_DIR/startup.log 2>&. &

echo $! > $PID_FILE
echo "rxas400adm started, PID=$(cat $PID_FILE)"
echo "Log file: $LOG_DIR/startup.log"
echo "API URL: http://localhost:$RXAS400_PORT/api/v."
```

### 3.2 stop.sh 停止脚本

```bash
#!/bin/sh
# ============================================================
# RXAS400ADM 停止脚本
# ============================================================

APP_HOME=/QOpenSys/rxas400
PID_FILE=$APP_HOME/rxas400adm.pid

if [ -f $PID_FILE ]; then
    PID=$(cat $PID_FILE)
    if kill -0 $PID 2>/dev/null; then
        echo "Stopping rxas400adm (PID: $PID)..."
        kill $PID
        sleep 5
        if kill -0 $PID 2>/dev/null; then
            echo "Force killing $PID..."
            kill -9 $PID
        fi
        echo "rxas400adm stopped."
    else
        echo "Process $PID not found."
    fi
    rm -f $PID_FILE
else
    echo "PID file not found."
fi
```

## H6: 从 mock 切换到正式环境

> 开发/演示阶段用 `mock` profile（AS400 走 `MockAS400Client` 假数据），上线必须切到 `prod`。
> 切换本身只改**一个启动参数**，但有一串连锁机制需要理解并逐项验证，否则会出现「启动成功但连的不是真机器」「演示数据混入生产」等隐蔽问题。

### 6.. 切换机制总览（代码依据）

| # | 机制 | 位置 | mock 模式行为 | prod 模式行为 |
|---|------|------|--------------|--------------|
| . | Profile 判定 | `ProfileResolver.isMockMode()` | active profile 含 `mock` 即为真 | 不含 `mock` 一律按生产处理（fail-secure） |
| 2 | **默认值陷阱** | `application.yml` L6 | `spring.profiles.active: mock` 是**默认值** | 启动命令**必须显式** `--spring.profiles.active=prod` 覆盖，漏写即静默起 mock |
| 3 | AS400 客户端切换 | `AS400ClientProviderImpl` | 每个"服务器"返回 `MockAS400Client`（假数据，服务器名仅作展示标识） | 按 `rx_ibmi_system` 表记录 `new JTOpenAS400Client(host, user, 解密密码)` 真连接 |

### 6.6 常见坑与排查

| # | 症状 | 根因 | 处置 |
|---|------|------|------|
| 坑 ① | 启动成功但所有页面都是"熟悉"的假数据 | 忘传 `--spring.profiles.active=prod`，yml 默认 mock 生效 | 日志找 MOCK 横幅；start.sh 补参数 |
| 坑 ② | prod 启动即抛 `IllegalStateException: 全新数据库在非 mock/dev profile...` | 新库无基础数据，DataInitializer fail-fast | 先按 init_rxadmin.sql 初始化再切 prod |
| 坑 ③ | 「测试连接」报解密失败/密码错误 | `rx_ibmi_system.password_encrypt` 是用**旧 KEY** 加密的，生产换了 `RXAS400_CRYPTO_KEY` | 用生产 KEY 在界面重新录入密码保存（重新加密），**不要**把开发库密文原样搬过来 |
| 坑 ④ | Flyway 校验失败拒启 | prod 开启 `validate-on-migrate: true`，迁移文件被改过或 checksum 漂移 | 只增不改：新变更一律新 V{n} 文件，禁止改历史脚本 |
| 坑 ⑤ | 前端能登录但 WebSocket 监控推送不通 | CORS 白名单没含前端来源（WS 握手同样受 CORS 管） | `RXAS400_CORS_ALLOWED_ORIGINS` 加上前端 origin 后重启 |
| 坑 ⑥ | 设了 `system.mock-mode-enabled=false` 后想临时回 mock 排查问题被拒启 | 这是设计行为（单向锁） | 临时 UPDATE 该配置为其他值 → 重启 mock → 排查完务必改回 false |
| 坑 ⑦ | 【已预防】prod 档首条 AS400 SQL 即报 AbstractMethodError | jt400 ...0 驱动连接实现无 JDBC4 isValid()，连接池默认校验路径失败 | **代码已内置兜底**（connectionTestQuery=SELECT . FROM SYSIBM.SYSDUMMY.）；后续升级 jt400 ≥20 后可移除 |
| 坑 ⑧ | 【上线前必查】存量 CL 脚本/操作模板执行报「包含被禁止的高危动词」 | S4 黑名单生效：CHGUSRPRF/CRTUSRPRF/DLTLIB/DLTF/CLRPFM/CHGSYSVAL/PWRDWNSYS 等 .7 动词默认拒绝 | 上线前盘点脚本清单；确需执行的运维动作改由具备权限的管理员在 IBM i 侧原生执行，或经评审后在 `rxas400.cl-blacklist.extra-verbs` 反向调整（黑名单只增不减原则下不建议放行） |
| 坑 ⑨ | IFS 上传/文档发布报「路径不在允许范围内」 | S. 白名单生效：读写路径必须位于 `rxas400.ifs.allowed-roots` 之下 | 默认 `/QOpenSys/rxas400` 已覆盖平台目录；如需开放其它根目录在 yml 追加并重启 |

### 6.7 回退方法

.. `stop.sh` 停止应用；
2. start.sh 将 profile 改回 `--spring.profiles.active=mock`；
3. 若此前已设置 mock 锁定：`UPDATE RX_CONFIG SET CONFIG_VALUE='true' WHERE CONFIG_KEY='system.mock-mode-enabled';`
4. 重启并确认 MOCK 横幅出现。
> ⚠️ 回退仅用于故障应急；生产库中产生的真实数据不会因回退丢失（mock 客户端只影响 AS400 读数，不碰业务表）。

## H7: 前端构建与 Nginx 反向代理

> 前端与后端同机部署在 US400CND：后端 8080 提供 API + WebSocket，前端静态文件由 Nginx 托管并反代 `/api`、`/ws` 到 8080。**WebSocket 反代漏配 Upgrade 头是最高频故障**（症状：能登录、监控推送全无）。

### 7.. 前端构建

```bash
# 开发机构建。VITE_API_BASE 默认 '/api/v.'（相对路径），走同域反代时无需设置
cd frontend
npm run build          # 产物 dist/（含 TS 类型检查）
```

| 构建变量 | 默认 | 何时需要改 |
|---------|------|-----------|
| `VITE_API_BASE` | `/api/v.` | 仅当前端与后端**不同源直连**（不走反代）时设为绝对地址如 `https://us400cnd.example.com/api/v.`；同域 Nginx 反代保持默认 |
| `VITE_API_PROXY_TARGET` | `http://localhost:8080` | 仅本地 `npm run dev` 的代理目标，**生产构建不使用** |

```bash
# 上传产物到 US400CND
# frontend/dist/ → /QOpenSys/rxas400/ui/
```

### 7.2 Nginx 配置样例（完整可用）

```nginx
server {
    listen       80;
    server_name  us400cnd;            # 或 IP

    # ── 前端静态资源 ──────────────────────────────
    root  /QOpenSys/rxas400/ui;
    index index.html;

    # Vue history 路由回退：刷新/直达深层路由不 404
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 静态资源缓存（Vite hash 文件名可长缓存）
    location /assets/ {
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # ── 后端 API 反代 ─────────────────────────────
    location /api/ {
        proxy_pass http://.27.0.0..:8080;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;   # 后端 S3 可信代理机制依赖此头
        proxy_read_timeout 60s;           # 慢查询（报表生成等）留足时间
        client_max_body_size 50m;         # IFS 文件上传 / 文档附件
    }

    # ── WebSocket 反代（STOMP，监控推送）──────────
    # ⚠️ 三行 Upgrade 头缺一不可，漏配 = 登录正常但实时曲线/通知全静默
    location /ws {
        proxy_pass http://.27.0.0..:8080;
        proxy_http_version ...;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host       $host;
        proxy_read_timeout 3600s;         # 长连接不被 Nginx 默认 60s 掐断
    }
}
```

### 7.3 网络端口开放清单

| 端口 | 开放范围 | 用途 |
|------|---------|------|
| 80 (Nginx) | 运维网段 | 用户访问 UI/API/WS 的唯一入口 |
| 8080 | **仅本机**（Nginx → 后端） | Spring Boot；不建议对网段直接暴露（绕过反代） |
| 8470 | 仅本机 | JTOpen DRDA（localhost 连接） |

> 若必须直连 8080 跳过 Nginx：前端需 `VITE_API_BASE=http://<ip>:8080/api/v.` 重新构建，且 CORS 白名单加前端 origin（见 H6 §6.5），WS 直连 `http://<ip>:8080/ws`。

### 4.2 Token 服务实现

```java
// JwtTokenService.java
@Service
@RequiredArgsConstructor
public class JwtTokenService {
    
    private final JwtEncoder jwtEncoder;
    private final JwtDecoder jwtDecoder;
    
    @Value("${rxas400.jwt.expire-ms}")
    private long accessTokenExpireMs;
    
    @Value("${rxas400.jwt.refresh-expire-ms}")
    private long refreshTokenExpireMs;
    
    /**
     * 生成 Access Token
     */
    public String generateAccessToken(UserDetails userDetails) {
        Instant now = Instant.now();
        String scope = userDetails.getAuthorities().stream()
            .map(GrantedAuthority::getAuthority)
            .collect(Collectors.joining(" "));
        
        JwtClaimsSet claims = JwtClaimsSet.builder()
            .issuer("rxas400adm")
            .issuedAt(now)
            .expiresAt(now.plusMillis(accessTokenExpireMs))
            .subject(userDetails.getUsername())
            .claim("scope", scope)
            .claim("token_type", "access")
            .build();
        
        return jwtEncoder.encode(JwtEncoderParameters.from(claims)).getTokenValue();
    }
    
    /**
     * 生成 Refresh Token
     */
    public String generateRefreshToken(UserDetails userDetails) {
        Instant now = Instant.now();
        
        JwtClaimsSet claims = JwtClaimsSet.builder()
            .issuer("rxas400adm")
            .issuedAt(now)
            .expiresAt(now.plusMillis(refreshTokenExpireMs))
            .subject(userDetails.getUsername())
            .claim("token_type", "refresh")
            .build();
        
        return jwtEncoder.encode(JwtEncoderParameters.from(claims)).getTokenValue();
    }
    
    /**
     * 刷新 Access Token
     */
    public TokenResponse refreshToken(String refreshToken) {
        try {
            Jwt<?> jwt = jwtDecoder.decode(refreshToken);
            String username = jwt.getSubject();
            String tokenType = jwt.getClaimAsString("token_type");
            
            if (!"refresh".equals(tokenType)) {
                throw new InvalidTokenException("Invalid refresh token");
            }
            
            // 验证 refresh token 是否在黑名单中
            // ... 
            
            // 生成新的 access token
            UserDetails userDetails = userDetailsService.loadUserByUsername(username);
            String newAccessToken = generateAccessToken(userDetails);
            String newRefreshToken = generateRefreshToken(userDetails);
            
            return TokenResponse.builder()
                .accessToken(newAccessToken)
                .refreshToken(newRefreshToken)
                .build();
                
        } catch (Exception e) {
            throw new InvalidTokenException("Invalid refresh token");
        }
    }
}

// TokenResponse.java
@Data
@Builder
public class TokenResponse {
    private String accessToken;
    private String refreshToken;
    private String tokenType;
    private long expiresIn;
}

// api/auth.ts
export interface TokenResponse {
  accessToken: string
  refreshToken: string
  tokenType: string
  expiresIn: number
}

export const login = (data: LoginCredentials) =>
  request.post<TokenResponse>('/auth/login', data)

export const refreshToken = (refreshToken: string) =>
  request.post<TokenResponse>('/auth/refresh', { refreshToken })

// stores/user.ts
export const useUserStore = defineStore('user', {
  state: () => ({
    accessToken: '',
    refreshToken: '',
    tokenExpireTime: 0
  }),
  
  actions: {
    async login(credentials: LoginCredentials) {
      const { data } = await login(credentials)
      this.accessToken = data.accessToken
      this.refreshToken = data.refreshToken
      this.tokenExpireTime = Date.now() + data.expiresIn * .000
      
      // 设置定时刷新
      this.scheduleTokenRefresh(data.expiresIn)
    },
    
    scheduleTokenRefresh(expiresIn: number) {
      // 在过期前 5 分钟刷新
      const refreshTime = (expiresIn - 300) * .000
      setTimeout(() => {
        this.refreshAccessToken()
      }, refreshTime)
    },
    
    async refreshAccessToken() {
      try {
        const { data } = await refreshToken(this.refreshToken)
        this.accessToken = data.accessToken
        this.refreshToken = data.refreshToken
        this.tokenExpireTime = Date.now() + data.expiresIn * .000
        
        this.scheduleTokenRefresh(data.expiresIn)
      } catch (error) {
        this.logout()
      }
    },
    
    logout() {
      this.accessToken = ''
      this.refreshToken = ''
      this.tokenExpireTime = 0
      router.push('/login')
    }
  }
})

// utils/request.ts
instance.interceptors.request.use((config) => {
  const userStore = useUserStore()
  
  // 检查 token 是否过期
  if (Date.now() > userStore.tokenExpireTime) {
    userStore.refreshAccessToken()
  }
  
  config.headers.Authorization = `Bearer ${userStore.accessToken}`
  return config
})

### 5.. 备份对象与频率

| 对象 | 方式 | 频率 | 说明 |

| RXADMIN Library | `SAVLIB LIB(RXADMIN) DEV(*SAVSYS)` 或 `SAVDEV` | 每日 | 全部业务表（用户/权限/审计/调度配置） |

> 🔴 **密钥保管是备份体系中最关键的一项**：
> - `RXAS400_CRYPTO_KEY` 丢失 → `rx_ibmi_system` 中全部服务器密码无法解密，**所有真机功能瘫痪**且不可修复（只能逐台重录密码）
> - `RXAS400_JWT_SECRET` 丢失 → 全员被登出（重新签发即可，损失小），但换新 KEY 前签发的 token 全部失效
> - 两把 KEY 明文只允许存在于：生产 .env 文件 + 一份离线纸质/加密存储

### 6.2 前端升级注意

- 直接替换 `/QOpenSys/rxas400/ui/` 内容即可（Vite hash 文件名天然免缓存问题）
- **index.html 必须不缓存**：Nginx 对 `location /` 的 index.html 加 `add_header Cache-Control "no-cache";`，否则用户停留在旧版引用已被删除的 hash 资源 → 白屏

### 6.3 回滚规则

| 场景 | 处置 |
|------|------|
| 新版启动失败（未执行迁移就挂了） | 换回旧 jar 重启即可，零残留 |
| 已成功执行新迁移后发现功能问题 | **禁止直接换旧 jar 了事**——DB schema 可能新于旧代码。评估二选一：<br>a) 若新迁移仅加列/加索引（向后兼容）：旧 jar 可直接跑<br>b) 若有破坏性 DDL：还原 M5 备份的 Library 至升级前状态再回滚 jar |
| 只想回滚前端 | 恢复 `ui.tgz` 备份 |

> 规范保障：本项目门禁要求**历史迁移文件永不修改**（prod `validate-on-migrate=true` 会拦截 checksum 漂移），新增变更一律新 V{n}，因此正常升级路径始终是安全的纯增量。

> IBM i PASE 没有 logrotate；Spring Boot 自带按天轮转但不删旧文件，放任不管会吃满 IFS。

### 7.. 清理脚本

```sh
# /QOpenSys/rxas400/cleanup-logs.sh —— ADDJOBSCHE 每周日 03:00
#!/bin/sh
LOGDIR=/QOpenSys/rxas400/logs
# 应用日志保留 30 天
find $LOGDIR -name "rxas400*.log*" -mtime +30 -delete
find $LOGDIR -name "*.gz" -mtime +30 -delete
# 启动日志保留 .0 份（追加模式则跳过）
ls -t $LOGDIR/startup*.log 2>/dev/null | tail -n +.. | xargs -r rm -f
# 备份目录由 backup.sh 自清理（M5），此处兜底
find /QOpenSys/rxas400/backup -maxdepth . -type d -mtime +35 -exec rm -rf {} \;
```

```clle
ADDJOBSCHE JOB(CL_RXAS400LOG) CMD(CALL PGM(QP2SHELL) +
  PARM('/QOpenSys/rxas400/cleanup-logs.sh')) FRQ(*WEEKLY) +
  SCDDAY(*SUN) SCDTIME(03000)
```

### 7.2 日志体积预估

| 来源 | 单日估算 | 说明 |
|------|---------|------|
| 应用日志 info 级 | ~5-20 MB | prod 已设 `com.rxas400adm: info`；采集轮次/调度心跳占大头 |
| 审计表（非日志但同属增长数据） | 与操作量相关 | `RX_AUDIT_LOG`/`RX_METRIC` 建议 MetricRetentionJob 的 `rxas400.monitor.retention-days`（默认 30 天）保持开启 |

## M8: 多节点部署

> 当前代码已具备多节点基础：Quartz JDBC JobStore 集群 + 监控采集分布式锁。扩展前逐项核对下表。

### 8.. 各组件多节点行为矩阵

| 组件 | 互斥机制 | 多节点行为 | 需要的配置 |
|------|---------|-----------|-----------|
| Quartz 作业/报表调度 | ✅ JDBC JobStore 集群（`isClustered: true`，checkin .5s） | 同一任务只会被一个节点触发 | 两节点必须连**同一数据库**；`instanceId: AUTO` 已配 |
| 监控采集 CollectorScheduler | ✅ `rx_dist_lock` 表锁 | 抢到锁的节点采集，另一节点本轮跳过 | 每个节点都设 `RXAS400_SCHEDULER_LOCK=true`（默认 false=不启用锁！） |
| 告警升级 AlertUpgradeService | ✅ 抢占式置位（单条 `UPDATE...WHERE id IN(...) AND upgrade_notified=0` 原子抢占 + 进程内 CAS 重入门禁） | 同批告警只会被一个节点处理；【2026-08-26 C7/P7 加固后竞态窗口归零】 | 严格互斥已内置；如需跨节点强一致可再叠加 rx_dist_lock |
| Token 黑名单清理等杂项 @Scheduled | ➖ 幂等删除/清理 | 双跑无副作用 | 无需处理 |
| HTTP 流量 | — | Nginx `upstream` 轮询两个节点 | `X-Forwarded-For` 透传链路保持（限流/IP 白名单依赖真实 IP） |
| WebSocket STOMP | — | simple broker 为**节点内存态**：用户 A 连在节点 .，节点 2 产生的推送 A 收不到 | 🔴 当前版本监控推送按连接所在节点路由，双节点需粘性会话（`ip_hash`）或改造外部 broker；单节点无此问题 |

### 8.2 第二个节点上线步骤

```bash
# 0. 前提：节点 . 正常运行（QRTZ_ 表已初始化）
# ⚠️ 不要两节点同时做首次冷启动：initialize-schema: always 并发建表会竞争；
#    先起节点 .，确认 QRTZ_ 表存在后再起节点 2

# .. 节点 2 部署相同 jar + 相同 .env（JWT_SECRET/CRYPTO_KEY 必须与节点 . 完全一致，
#    否则一边签发的 token 另一边验不过 / 加密密码解不开）

# 2. 节点 2 设置采集锁（节点 . 也要补设）
export RXAS400_SCHEDULER_LOCK=true

# 3. Nginx upstream 化
upstream rxas400_backend {
    ip_hash;                       # WebSocket 粘性会话
    server .27.0.0..:8080;         # 节点 .
    server <node2-ip>:8080;        # 节点 2
}
# proxy_pass http://rxas400_backend;

# 4. 验证：停掉节点 . → 调度任务在节点 2 正常触发（QRTZ 集群接管 ≤.5s+misfire 阈值）
```

### 8.3 何时值得上双节点

| 场景 | 建议 |
|------|------|
| 纯高可用（防单点宕机） | ✅ 收益明确，按上述步骤 |
| 性能扩容 | ❌ 本系统瓶颈通常在 IBM i 单机（JTOpen/QSYS2 查询），双节点不提升 AS400 侧吞吐 |
| 灰度发布 | ❌ 当前无服务注册发现，直接整节点切换更简单可控 |
