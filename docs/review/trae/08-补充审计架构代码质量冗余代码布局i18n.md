### 8.1 架构层面

#### [规范警告/Warning] Service 层缺乏面向接口编程，仅 `SysUserService` 有接口

> **AAA-Remark（2026-08-15 复核）**：✅ 真实存在——`service` 包共 17 个文件，仅 `SysUserService`（接口）+ `SysUserServiceImpl`（实现）成对；其余 15 个均为具体类（含 `SysConfigService`）。接口化对 `MenuService`/`RoleService`/`PermissionManageService` 有价值，但注意 Spring 用 CGLIB 代理、现有调用方全是具体类注入，抽取接口是纯增量、可渐进。

**文件**：`backend/.../service/*.java`

**问题**：17 个 Service 类中，仅 `SysUserServiceImpl` 实现了 `SysUserService` 接口，其余 16 个（`MenuService`, `RoleService`, `DocService`, `WebhookService`, `PermissionManageService` 等）均为具体类直接注入。Spring 默认使用 CGLIB 动态代理，不强制要求接口，但这导致：

- 新人无法通过"跳转到接口"快速理解服务契约（只能看到实现细节）
- 单元测试时无法用 Mockito 接口 mock，必须用 `@MockBean` 或 `@SpyBean` 对具体类操作
- 缺少"契约先行"的约束，API 变更时接口编译期即可发现调用方

**重构建议**：为核心 Service（至少 `MenuService`, `RoleService`, `PermissionManageService`）抽取接口。

```java
// 易读重构：MenuService 接口化
public interface MenuService {
    List<MenuVO> enabledMenuTree();
    List<MenuVO> userMenuTree(String username);
    UserMenuDataVO userMenuData(String username);
    // ...
}

@Service
@RequiredArgsConstructor
public class MenuServiceImpl implements MenuService {
    // ...
}
```

#### [规范警告/Warning] `@Transactional` 缺少 `rollbackFor` 声明

**文件范围**：`WebhookService.java`, `SysUserServiceImpl.java`, `DocService.java`, `RegionService.java`, `PermissionRequestService.java`, `NotificationService.java`, `NoticeService.java`

**问题**：大量 `@Transactional` 注解未指定 `rollbackFor = Exception.class`，仅使用默认值。Spring 默认只在 `RuntimeException` 和 `Error` 时回滚，**checked exception（如 `BusinessException` 继承自 `RuntimeException` 则不受影响，但团队未统一约定）**。如果 `BusinessException` 继承链有变更或新人抛出 checked exception，事务不会回滚，造成数据不一致。

```java
// 原代码：不安全的写法
@Transactional  // 默认仅 RuntimeException 回滚
public void create(SysUser user) { ... }

// 易读重构：显式声明
@Transactional(rollbackFor = Exception.class)  // 任何异常都回滚
public void create(SysUser user) { ... }
```

**对比**：`RoleService` 和 `PermissionManageService` 正确使用了 `@Transactional(rollbackFor = Exception.class)`，应作为团队规范统一推广。

> **AAA-Remark（2026-08-15 复核）**：✅ 真实存在——全库 55 处 `@Transactional` 无 `rollbackFor`、22 处带 `rollbackFor`；6 个 Service 已正确（Dict/Favorite/Menu/PermissionManage/Role/UserMenu）。⚠️ 本文 §8.1 此处说「7 个 Service 缺」与 §11.1 全量扫描「14 个 Service 缺」口径不同（8.1 为抽查、11.1 为全量，以 §11.1 为准）。修复属纯注解改动，低风险，可批量（§11.1 步骤二有 IDE 正则方案）。

#### [重构建议/Info] 后端模块边界模糊，`common` 模块承载过重

> **AAA-Remark（2026-08-15 复核）**：属架构取舍，无对错。安全相关已独立为 `rxas400adm-security` 模块，common 内剩余多为跨模块基础设施；拆分需评估依赖面，收益不如 §2.1/§10.1 的问题直接，建议降级为 Info。

**问题**：`rxas400adm-common` 模块包含了异常处理、安全（密码策略、Token 混淆、AES 加密）、响应封装、事件发布、Webhook 通知、Caffeine 缓存等大量职责。虽然命名为 "common"，但实际承载了跨模块基础设施，建议按职责拆分为 `rxas400adm-security`、`rxas400adm-cache`、`rxas400adm-notify` 等子模块，降低 common 的认知负担。

// 一次 IN 查询 + 分组，替代逐角色 1 次查询的 N+1
private void fillMenuIds(List<SysRole> roles) {
    if (roles.isEmpty()) return;
    List<Long> roleIds = roles.stream().map(SysRole::getId).toList();
    Map<Long, List<Long>> grouped = roleMenuMapper.selectList(
            new LambdaQueryWrapper<SysRoleMenu>().in(SysRoleMenu::getRoleId, roleIds))
            .stream().collect(Collectors.groupingBy(...));
    roles.forEach(r -> r.setMenuIds(grouped.getOrDefault(r.getId(), List.of())));
}
```

    if (roleMapper.selectById(roleId) == null) {  // 额外查一次
        throw new BusinessException("角色不存在: " + roleId);
    }
    SysUserRole ur = new SysUserRole();
    ur.setUserId(userId);
    ur.setRoleId(roleId);
    userRoleMapper.insert(ur);  // N 次 INSERT
}
```

**建议**：使用 MyBatis-Plus 的 `saveBatch()` 或自定义 Mapper 的批量 INSERT。

```java

    .map(roleId -> { SysUserRole ur = new SysUserRole(); ur.setUserId(userId); ur.setRoleId(roleId); return ur; })
    .toList();
userRoleMapper.insertBatch(userRoles);  // 一条 INSERT INTO ... VALUES (...), (...), (...)
```
