# 二、类型安全与契约（新人理解的核心）

### 2.1 前端 TypeScript 类型审计

#### [阻碍理解/Blocker] `request.ts` 类型断言断裂

> **AAA-Remark（2026-08-15 复核）**：✅ 真实存在——`request.ts` 共 5 处 `as unknown as`（拦截器 L90 + 四个方法 L129/132/135/138），全库另有 3 处（`calendar/index.vue` L108、`data/sysvals/index.vue` L158、`i18n/index.ts` L28），合计 **8 处**（文档附录「4 处」低估）。响应拦截器确实已做 `res.data` 解包，文档建议的 axios 泛型重构方向可行、风险低；改后需与 §5.2 的 `data: T | null` 标注同步处理，属最高优先级建议。

**文件**：[request.ts](file:///d:/vueprojects/RXAS400ADM/frontend/src/api/request.ts#L127-L140)

**问题**：所有 HTTP 方法均使用 `as unknown as Promise<T>` 绕过类型检查，导致调用方声明的泛型 `<T>` 与实际运行时返回类型完全脱钩——编译器不会报错，但运行时数据形状可能完全不同。

```typescript
// 原晦涩代码（request.ts L127-L140）
const request = {
  get<T = unknown>(url: string, config?: AxiosRequestConfig): Promise<T> {
    return instance.get(url, config) as unknown as Promise<T>; // 类型断言黑洞
  },
  post<T = unknown>(
    url: string,
    data?: unknown,
    config?: AxiosRequestConfig,
  ): Promise<T> {
    return instance.post(url, data, config) as unknown as Promise<T>;
  },
  // ...
};
```

**根因**：响应拦截器 L109 做了 `return res.data as unknown as typeof response`，导致 axios 原始响应类型被破坏，方法签名无法正确推断。

**影响**：新人调用 `request.get<UserVO>('/users')` 时 TS 不报错，但实际返回可能是 `{ code: 0, message: "success", data: {...} }` 的未解包形式，调试时才发现数据路径错误。

**重构建议**：

```typescript
// 易读重构代码：利用 axios 响应拦截器类型覆盖
import type { AxiosResponse } from "axios";

// 1. 在 instance 上声明拦截器返回类型
instance.interceptors.response.use(
  (response: AxiosResponse<ApiResponse<unknown>>) => {
    const res = response.data;
    if (res.code !== 0) {
      ElMessage.error(res.message || i18n.global.t("common.requestFailed"));
      return Promise.reject(new Error(res.message));
    }
    // 返回解包后的 data，同时保留 response 其他字段（headers 等）
    return { ...response, data: res.data } as AxiosResponse<unknown>;
  },
  // ...
);

// 2. 方法签名利用 axios 泛型推断，无需 as unknown as
const request = {
  get<T>(url: string, config?: AxiosRequestConfig): Promise<T> {
    return instance.get<T>(url, config).then((r) => r.data);
  },
  post<T>(
    url: string,
    data?: unknown,
    config?: AxiosRequestConfig,
  ): Promise<T> {
    return instance.post<T>(url, data, config).then((r) => r.data);
  },
  put<T>(url: string, data?: unknown, config?: AxiosRequestConfig): Promise<T> {
    return instance.put<T>(url, data, config).then((r) => r.data);
  },
  delete<T>(url: string, config?: AxiosRequestConfig): Promise<T> {
    return instance.delete<T>(url, config).then((r) => r.data);
  },
};
```

#### [规范警告/Warning] `useTablePage` 泛型与 `unknown` 逃逸

> **AAA-Remark（2026-08-15 复核）**：✅ 真实存在——`TablePageQueryParams` 确有 `[key: string]: unknown` 索引签名。该 composable 已被 20+ 页面使用，泛型化改造需同步全部调用方；属 Info 级优化，新人可通过调用处显式收窄缓解，不必急于重构。

**文件**：[useTablePage.ts](file:///d:/vueprojects/RXAS400ADM/frontend/src/composables/useTablePage.ts#L44-L53)

**问题**：`TablePageQueryParams` 使用 `[key: string]: unknown` 索引签名，`fetchApi` 参数类型过于宽松，调用方需要手动 `as string` 类型收窄。

```typescript
// 原代码
export interface TablePageQueryParams {
  current?: number;
  size?: number;
  keyword?: string;
  [key: string]: unknown; // 逃逸 hatch
}
```

**重构建议**：泛型化 `UseTablePageOptions`，让调用方传入自定义参数类型。

```typescript
// 易读重构
export interface UseTablePageOptions<
  T,
  P extends TablePageQueryParams = TablePageQueryParams,
> {
  fetchApi: (params: P) => Promise<TablePageResponse<T> | T[]>;
  buildParams?: (base: {
    current: number;
    size: number;
    keyword?: string;
  }) => P;
  // ...
}

// 调用方（Job 页面）
interface JobQueryParams extends TablePageQueryParams {
  tab?: "all" | "msgw" | "lckw";
}
const { pagedData } = useTablePage<JobInfo, JobQueryParams>({
  fetchApi: (params) => fetchJobs(params), // params.tab 有类型提示
});
```

### 2.2 后端 DTO/VO/Entity 分层审计

#### [规范警告/Warning] `MenuService` 大量使用 `Map<String, Object>` 传输菜单数据

> **AAA-Remark（2026-08-15 复核）**：✅ 真实存在——`MenuService` 有 10+ 个方法返回 `Map<String, Object>`（`toMenuMap`/`toMenuMapFull`/`userMenuData`/`userTabs` 等）。补充：合订本轮次已修复 MenuService 的 N+1（双份流内 selectById → selectBatchIds），但 Map 传输仍是最大可读性债。§7 Action Item 1 的 MenuVO 方案与分层准绳 R3 方向一致，建议优先实施。→ **状态：N+1 ✅ 已修复（轮次 12 selectBatchIds）；Map 传输 ⏳ 未修**

**文件**：[MenuService.java](file:///d:/vueprojects/RXAS400ADM/backend/rxas400adm-system/src/main/java/com/rxas400adm/system/service/MenuService.java#L263-L295)

**问题**：`toMenuMap()`、`toMenuMapFull()`、`userMenuData()` 等方法返回 `List<Map<String, Object>>` 或 `Map<String, Object>`，前端调用时完全不知道 `map.put("path", ...)` 的 key 有哪些，契约是隐式的。

```java
// 原晦涩代码（MenuService.java L263-L295）
private Map<String, Object> toMenuMap(SysMenu menu) {
    Map<String, Object> map = new LinkedHashMap<>();
    map.put("path", menu.getPath());
    map.put("title", menu.getTitle());
    if (StringUtils.hasText(menu.getIcon())) {
        map.put("icon", menu.getIcon());
    }
    if (menu.getChildren() != null && !menu.getChildren().isEmpty()) {
        map.put("children", menu.getChildren().stream().map(this::toMenuMap).toList());
    }
    return map;
}
```

**影响**：新人修改菜单字段时，需要同时搜索 `map.put("path"`、`map.put("title"` 等字符串，极易遗漏；前端 `MenuNode` 接口与后端 `Map` 的契约完全靠"约定"。

**重构建议**：定义具名 VO 类。

```java
// 易读重构代码：定义 MenuVO 替代 Map<String, Object>
@Data
@Builder
public class MenuVO {
    private String path;
    private String title;
    private String icon;
    private List<MenuVO> children;
}

// 替换 toMenuMap
private MenuVO toMenuVO(SysMenu menu) {
    return MenuVO.builder()
        .path(menu.getPath())
        .title(menu.getTitle())
        .icon(menu.getIcon())
        .children(menu.getChildren() != null
            ? menu.getChildren().stream().map(this::toMenuVO).toList()
            : null)
        .build();
}
```
