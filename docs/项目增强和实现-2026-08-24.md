## 一、功能增强（待实施）

### E1: 告警未处理自动升级

**功能描述**：告警产生后，若指定时间内未处理，自动通知管理员

**配置参数**：
```yaml
rxas400:
  alert:
    upgrade:
      enabled: false  # 功能开关，默认关闭
      check-interval-minutes: 5  # 检查间隔（分钟）
      upgrade-after-minutes: 30  # 未处理多久后升级（分钟）
      notify-role: ADMIN  # 升级通知的角色
      notify-channels:  # 通知渠道
        - WEBHOOK
        - NOTIFICATION  # 站内通知
```

**实现要点**：
- 定时任务定期检查未处理告警（`RX_ALERT_EVENT.STATUS != 'RESOLVED'`）
- 超过配置时间未处理 → 发送站内通知给指定角色
- 支持通过管理界面动态开关

**数据库变更**：
```sql
-- 告警事件表添加升级时间字段
ALTER TABLE RX_ALERT_EVENT ADD COLUMN UPGRADE_TIME TIMESTAMP;
ALTER TABLE RX_ALERT_EVENT ADD COLUMN UPGRADE_NOTIFIED SMALLINT DEFAULT 0;
```

**预估工时**：4-6小时

### E3: 操作审计日志增强

**功能描述**：记录操作时间、命令、数据表、操作人等关键信息

**审计日志字段**：
```sql
CREATE TABLE RX_AUDIT_LOG (
    ID BIGINT PRIMARY KEY,
    USER_NAME VARCHAR(50),        -- 操作人
    ACTION VARCHAR(50),            -- 操作类型（CREATE/UPDATE/DELETE/EXECUTE）
    MODULE VARCHAR(50),            -- 模块（JOB/IFS/SYSTEM/...）
    TARGET VARCHAR(200),           -- 操作对象（作业名、文件路径、表名）
    IP VARCHAR(255),               -- 操作IP
    DETAIL TEXT,                   -- 操作详情（命令、参数、影响行数）
    RESULT VARCHAR(20),            -- 操作结果（SUCCESS/FAIL）
    COST_MS BIGINT,                -- 执行耗时（毫秒）
    CREATED_TIME TIMESTAMP         -- 操作时间
);
```

**增强@OperateLog注解**：
```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface OperateLog {
    String module() default "";
    String operation() default "";
    boolean recordDetail() default true;  // 是否记录详情
    boolean recordTarget() default true;  // 是否记录操作对象
}
```

**预估工时**：4-6小时

export function useShortcuts() {

    'ctrl+/': () => showShortcutsHelp(),
    'escape': () => closeAllDialogs()

  onMounted(() => {
    Object.entries(shortcuts).forEach(([key, handler]) => {
      hotkeys(key, handler)
    })
  })
  
  onUnmounted(() => {
    hotkeys.unbindAll()
  })
}

### 3.1 useFormDialog 弹窗校验失效（🔴 已修复）

**问题描述**：`useFormDialog` 的 `onSubmit` 中，当 `saveApi` 用 `return` 做校验失败时（而非 `throw`），`onSubmit` 无法感知校验失败，仍然：
1. 显示成功提示
2. 关闭弹窗
3. 调用 `onSuccess` 刷新列表

**根因**：`validate: false` 禁用了 el-form 标准校验，`saveApi` 内的 `return` 只是退出函数，不影响 `onSubmit` 的后续流程。

**影响范围**：4 个页面（assets/schedule/scripts/sla）有此问题，其余 `validate: false` 页面（messageFiles/alertRules/config）的 `saveApi` 无自定义校验，不触发此 bug。

**修复方案**：将 4 个页面从 `validate: false` + `saveApi` 内校验，改为 **el-form rules** 标准校验：

| 页面 | 校验规则 |
|---|---|
| assets | name/host 必填 + 新建时 password 必填（自定义 validator） |
| schedule | name/serverId/command/cronExpr 必填 |
| scripts | name/command 必填 |
| sla | jobName/expectedDurationSec 必填（数据变量重命名 `rules`→`slaRules` 避免冲突） |

**Preview 验证**：不填任何字段点 Save → 弹窗保持打开，内联显示红色验证错误 ✅

## 六、配置「前端可维护化」评估——以 CL 高危动词黑名单为切入点（2026-08-26，✅ P1~P3 已实现）

> 触发问题：黑名单当前如何维护？能否前端/数据表维护？是否很麻烦？项目里还有哪些同类配置值得一并调整？

### 6.1 CL 黑名单现状与痛点确认

| 维度 | 现状 |
|---|---|
| 内置基线 | `DangerousClCommandValidator.BUILTIN_VERBS` **硬编码 17 个动词**于 Java 源码 |
| 扩展动词 | `rxas400.cl-blacklist.extra-verbs` 走 application.yml @Value 注入 |
| 开关 | `rxas400.cl-blacklist.enabled` 同为 yml @Value，默认 true |
| 变更流程 | 改 yml → 重启应用；无操作界面、无审计留痕、无变更历史 |
| 痛点结论 | **属实麻烦**：上线后想追加一个拦截动词需要「改配置文件 + 找窗口重启」，且不可追溯 |

### 6.2 可行性结论：✅ 强烈建议前端化，且成本极低

项目已有三块现成基础设施可直接复用，无需新建表/页面/权限：

| 基础设施 | 位置 | 复用方式 |
|---|---|---|
| `rx_config` KV 表 + SysConfigService + 「系统配置」管理页（SYS_CONFIG_MANAGE 权限 + @OperateLog 审计） | system 模块 | 黑名单键作为普通配置行，管理员在既有页面直接编辑 |

| 类型化绑定样板 | AlertUpgradeProperties / security 五个 Properties | 若保留 Properties 形态仅换读取源 |

### 6.3 推荐方案

**方案 B（推荐·轻量）：内置基线留代码，扩展项迁 rx_config**

| 键 | 内容 | 维护方式 |
|---|---|---|
| `cl.blacklist.extra-verbs` | 逗号分隔追加动词（原 yml extra-verbs 平移） | 「系统配置」页编辑，实时生效 |
| `cl.blacklist.enabled` | true/false | 同上 |

- 内置 17 动词保持硬编码：属安全基线，应随代码评审/版本走，不宜被运行时清空；
- Validator 改造：删两处 @Value → 注入 SysConfigService + 缓存失效机制；
- UI 可选增强：对这两个 key 渲染 tag 输入框，并只读展示内置基线清单——「内置(只读)/扩展(可编辑)」分区最清晰；
- **工时预估 0.5~1 天**（含缓存失效、单测、i18n）。

**方案 C（暂不推荐）：专表 rx_cl_blacklist 行式 CRUD + 独立页面**
- 独立权限码+页面+审计，工时 4~6h+；当前 17+N 规模下收益不抵成本。
